# Close audio, recording and control gaps first

StreamDeck's compositor-plus-GStreamer core is architecturally ahead of every open-source presenter we studied, but the roadmap that sits on top of it is lopsided: it plans deep work on slide capture, overlays and PowerPoint-grade rendering while omitting audio, local recording, a control API, a stage display and any ingest path for Mevo cameras that lack NDI. FreeShow, the closest open competitor, pushes every output through a GPU-to-CPU readback and a hidden-canvas WebRTC hack, and its "Scenes" hold a single media source; OBS, CasparCG and voctomix show that the hard parts we face (frame-clocked transitions, encoder fallback, congestion handling) are solved by a few small, copyable ideas rather than by heavy machinery. The largest risks are F3.2 (capturing our own presentation webview), F3.4 (alpha overlays from a transparent webview), F4.2 (encode-once fan-out through `whipclientsink`) and F5.1 (PowerPoint-indistinguishable rendering). Three of our own assumptions need correcting: Rust 1.78 in CLAUDE.md is far below what gst-plugins-rs (1.92) and Cap (1.88) require, the MIT `scap-direct3d` crate drags in an unlicensed, probably-AGPL sibling crate, and "zero dependency by Phase 5" contradicts the roadmap's own Phase 6 "external tools optional" gate while ignoring that NDI, GStreamer plugins and the Mevo cameras themselves remain external. Our recommended order is: promote SRT/RTMP ingest and egress, add audio and recording, ship a Rust-owned control API with a Companion module, replace F3.2/F3.4 screen-capture-first designs with frame injection plus native overlays, adopt voctomix-style control-source transitions for F3.3, and build encoder auto-selection by running test encodes.

## Competitors split into renderers, mixers and relays, and none combines all three

The tools we studied fall into three architectural families, and StreamDeck is trying to be all of them at once. **Presenters** (FreeShow, ProPresenter, OpenLP) own a slide model and an output window; **mixers** (OBS, CasparCG, voctomix) own a frame clock and a compositor; **relays** (MediaMTX) only remux. Understanding which family each feature comes from explains where our roadmap is thin.

FreeShow is the instructive failure case for the presenter family. It is Electron 37 with Svelte 3, about 216k lines, GPL-3.0, with one Chromium `BrowserWindow` per output running the same app ([OutputLifecycle.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/output/helpers/OutputLifecycle.ts)). (code) Every egress (NDI, Open Media Transport, Blackmagic SDI, WebRTC, RTMP, recorder, stage) takes raw BGRA read back from the GPU, and the code is dominated by throttling to contain that cost: adaptive pipeline depth, pool caps, memory-based back-pressure, and a source comment that several 4K surfaces at 60 fps balloon each readback from about 20 ms to about 100 ms ([CaptureHelper.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/capture/CaptureHelper.ts)). (code) Its RTMP path pipes raw frames into an external `ffmpeg` child with one `-c copy` relay per destination, backing off 1 to 15 s and probing hardware encoders ([RtmpStreamer.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/streaming/RtmpStreamer.ts)); its WHIP path pushes frames into a hidden canvas and lets Chromium encode ([WebRtcHost.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/streaming/WebRtcHost.ts)). (code) A FreeShow "Scene" is one source (camera, screen, NDI) plus style and overlays, with no geometry or picture-in-picture ([SceneMedia.svelte](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/components/output/layers/SceneMedia.svelte)), and its transitions are DOM/CSS effects with author-flagged glitches ([transitions.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/utils/transitions.ts)). Its strength is breadth: about 150 API actions behind WebSocket, REST and OSC, MIDI, four built-in web apps, roughly 30 importers, scripture with voice-triggered references, Web Audio mixing and cloud sync ([api.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/utils/api.ts)). (code) Its weaknesses are equally visible: 13 test files, about 3,000 `any` casts, plaintext provider secrets, a single optional shared password accepted in query strings over plain HTTP with CORS `*`, and API actions that execute inside the controller renderer so a hung renderer stops all remote control. (code) Its own issue tracker lists CCLI integration and a transitions rework as the top requests ([Issues](https://github.com/ChurchApps/FreeShow/issues)), and a March 2026 Blackmagic thread reports transitions running at about 3 fps at 1080p60 ([Issue #124](https://github.com/ChurchApps/FreeShow/issues/124)). (docs)

ProPresenter 7 and later (closed source, macOS and Windows only) is an output renderer with light production features: multiple simultaneous screens including SDI, NDI and Syphon, layered props and masks, RTMP/RTMPS streaming and recording of a configured output screen since 7.1, a documented REST-style API on port 50000 since 7.9 with a published OpenAPI spec, an official Stream Deck plugin, and a native PowerPoint importer only from 21.2 in February 2026 ([release notes](https://renewedvision.com/propresenter/release-notes), [API](https://renewedvision.com/propresenter/api/), [7.1 blog](https://renewedvision.com/blog/propresenter-7-1-the-live-stream-update)). (docs) The sources show no multi-camera switching, no WHIP and no multi-destination restreaming, though that is absence-based. Complaints centre on Windows feeling like a Mac port, resource use and subscription cost, reported at $289 per seat per year ([Capterra](https://www.capterra.com/p/170172/ProPresenter/reviews/?page=5), [Software Advice](https://www.softwareadvice.com/worship/propresenter-profile/), [GetApp](https://www.getapp.com.au/software/118675/propresenter)). (docs, reported) Mevo Studio, the other tool we aim to retire, is a phone and tablet app only (iOS 16+, Android; no desktop), at v4.2.4, with free single-destination streaming and a Pro tier at $19 per month for multistream and NDI|HX ([App Store](https://apps.apple.com/ba/app/mevo-studio/id1503021034), [Mevo Pro](https://www.mevo.com/pages/pro)). (docs) Cameras send raw video to the phone over a proprietary transport (TCP 38000/38001, UDP 61000-63000) and the phone encodes the program ([Mevo network help](https://help.mevo.com/hc/en-us/articles/360058647952-Multicam-Configuration-and-Setup)), so only the cameras' standard outputs are interoperable. (docs, snippet-sourced)

Among mixers, OBS is the reference for the frame loop. A single graphics thread renders to one GPU texture, scales and converts to YUV on the GPU, reads back only the final planes into a double-buffered staging surface mapped one frame later, and skips readback entirely for texture encoders (NVENC, AMF, QSV, VAAPI) via shared NV12 textures ([obs-video.c](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/libobs/obs-video.c), [obs-video-gpu-encode.c](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/libobs/obs-video-gpu-encode.c)). (code) When rendering falls behind, it sleeps to an absolute target and repeats the last frame to fill the timeline, counting "lagged" frames; when the encoder falls behind it drops and counts "skipped" frames. (code) OBS has no runtime encoder fallback chain: selection is a setting, a one-shot wizard picks NVENC over QSV over Apple over AMD, and a failed start shows an error ([AutoConfig.cpp](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/frontend/wizards/AutoConfig.cpp), [obs-output.c](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/libobs/obs-output.c)). (code) Its RTMP output measures send-queue duration, derives congestion as duration over a 700/900 ms threshold, drops disposable frames first, and, when the encoder allows, lowers bitrate to the measured throughput and recovers 10% every 4 s ([rtmp-stream.c](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/plugins/obs-outputs/rtmp-stream.c)). (code) Its WHIP output (libdatachannel, Opus audio only) contains no TWCC, REMB or congestion code in the plugin ([whip-output.cpp](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/plugins/obs-webrtc/whip-output.cpp)). (code) Windows window capture picks Windows Graphics Capture for the PowerPoint slideshow (`screenClass`) and Presenter View (`PodiumParent`) window classes and defaults most other windows to BitBlt ([window-capture.c](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/plugins/win-capture/window-capture.c)); macOS uses ScreenCaptureKit with zero-copy IOSurface binding and Linux uses the PipeWire portal with dmabuf import falling back to CPU memory. (code) Transitions are sources holding an A and a B child rendered to offscreen textures, with progress computed from the graphics thread's own clock rather than a UI timer ([obs-source-transition.c](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/libobs/obs-source-transition.c)). (code)

CasparCG and voctomix are the two transition references. voctomix builds one `compositor`, binds a `GstController` control source in step mode to each pad's `xpos`, `ypos`, `width`, `height`, `alpha` and `zorder`, and pre-computes every frame of a transition as timestamped values so the GStreamer streaming thread applies them; inactive sources are parked at alpha 0 and zorder -1 rather than unlinked ([scene.py](https://github.com/voc/voctomix/blob/173287ba60ce77c0595477f97c904f513de12c4d/voctocore/lib/scene.py), [videomix.py](https://github.com/voc/voctomix/blob/173287ba60ce77c0595477f97c904f513de12c4d/voctocore/lib/videomix.py)). (code) It runs 1080p25 I420 on the CPU with 3 s queues, so it is a stability design, not a low-latency one; it is MIT. CasparCG runs a real-time thread per channel over an OpenGL or Vulkan mixer with 30 blend modes, models transitions (mix, wipe, slide, push, cut, fadecut, cutfade, vfade) as producers that blend old and new frames, and renders HTML templates through windowless CEF with an AMCP command set that calls `play()/stop()/next()/update(data)/remove()` in the page ([transition_producer.cpp](https://github.com/CasparCG/server/blob/fe19ac0e36bf1d3f080f06ef161dafc4d73caacc/src/core/producer/transition/transition_producer.cpp), [html_producer.cpp](https://github.com/CasparCG/server/blob/fe19ac0e36bf1d3f080f06ef161dafc4d73caacc/src/modules/html/producer/html_producer.cpp)). (code) Its CEF frames arrive by CPU `memcpy` into a four-frame drop-oldest queue, with the last frame re-served when the page does not repaint; a Windows-only D3D11 shared-texture path exists, and a source comment says the CPU path measured faster on Linux. (code) It is GPL-3.0 and requires an OpenGL 4.5 GPU.

MediaMTX is the relay reference: a zero-dependency Go binary, MIT, that ingests and serves WHIP/WHEP, SRT, RTMP, RTSP, HLS and MoQ, forwards one path to several RTMP(S), SRT, RTSP, WHIP or MoQ destinations with a fixed 5 s retry and per-destination byte counters, records fMP4 in 1 s parts, and exposes a REST control API, Prometheus metrics (including a rich `srt_conns_*` set) and hooks ([forward/manager.go](https://github.com/bluenviron/mediamtx/blob/0cf5719cf504ddc046bb4df3636fdb6d942c20a1/internal/forward/manager.go), [metrics.go](https://github.com/bluenviron/mediamtx/blob/0cf5719cf504ddc046bb4df3636fdb6d942c20a1/internal/metrics/metrics.go)). (code) It never transcodes, so per-destination bitrate or resolution variants need separate encodes upstream; per-destination health beyond a byte counter is thin. ## Where our roadmap is on par, ahead, over-scoped or under-scoped

Measured against these tools, the shipped half of StreamDeck is competitive. Phase 1 slide control (import, state machine, notes, timer, multi-display with hotplug fallback) matches FreeShow's and OpenLP's baseline, and our Rust-owned state machine avoids FreeShow's renderer-executes-everything failure mode (inferred from [api.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/components/actions/api.ts)). F2.3's per-source throttle (8 fps previews, 1 s stats) is the same design as FreeShow's idle-at-1-fps and per-consumer frame budgets. F2.4's axum WHIP server is ahead of `whipserversrc`, which has no auth or TLS, answers `PATCH` with 501 and always returns 200 on delete ([whip_signaller/imp.rs](https://gitlab.freedesktop.org/gstreamer/gst-plugins-rs/-/blob/9cb42da34f16dd4e2679495a8f546518d863e57c/net/webrtc/src/whip_signaller/imp.rs)); our slot accounting, 409/503/401 handling and keychain token are real additions. F3.1 is ahead of FreeShow's single-source scenes on structure, and its `d3d12compositor` GPU path is the direction OBS and CasparCG took, though our digest reports only partial attainment of the latency target (CPU compositor about 33 ms p50, `d3d12compositor` about 49.5 ms p50) and the `glvideomixer` path is untested. Both are digest figures, not re-measured here.

The over-scoped items are F5.1 and F5.2. "Visually indistinguishable from PowerPoint" at 4K is not achieved by any competitor: FreeShow's parser admits missing shapes, tables and charts and imports no slide transitions or animations (code comments and an absence grep), ProPresenter shipped a native PowerPoint importer only in 2026, and OpenLP preserves fidelity only by remote-controlling real PowerPoint ([powerpointImporter.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/converters/powerpoint/powerpointImporter.ts)). FreeShow's own fallback is LibreOffice-to-PDF, which validates the hybrid we already half have: PDFium-rendered pages for fidelity, structured text for notes and search. The editor in F5.2 sits on a similar cliff: FreeShow's history layer alone is a 966-line switch with a whole-state save that silently drops concurrent saves ([save.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/data/save.ts)). F3.4's classifier-driven automatic overlay with a WCAG check is also generous scope for a feature whose rendering mechanism is unproven, and F6.1 FullAuto switching has no competitor precedent beyond OBS-style hotkeys and FreeShow's action chains. F4.2's "encode once, tee to many `whipclientsink`" is the most subtle over-reach: the gst README states encoding is not shared between consumers and per-session congestion control wants a different bitrate per destination, which an encode-once design cannot give (inferred from [README](https://gitlab.freedesktop.org/gstreamer/gst-plugins-rs/-/blob/9cb42da34f16dd4e2679495a8f546518d863e57c/net/webrtc/README.md) and [webrtcsink imp.rs](https://gitlab.freedesktop.org/gstreamer/gst-plugins-rs/-/blob/9cb42da34f16dd4e2679495a8f546518d863e57c/net/webrtc/src/webrtcsink/imp.rs)).

The under-scoped items are the ones that decide whether Mevo Studio can actually be retired. F4.4 (SRT ingest, "optional") is labelled backwards: SRT is the only standard output present on every Mevo camera, while NDI works only on Start and Core and HDMI only on Core ([Mevo output help](https://help.mevo.com/hc/en-us/articles/34335555416980-How-to-output-your-Mevo-Camera-via-HDMI-SRT-NDI-or-UVC-Webcam)). (docs, snippet-sourced) F2.2's NDI work carries unplanned cost: neither DistroAV nor gst-plugin-ndi bundles the runtime, both loading it lazily and requiring the user to install it ([DistroAV README](https://github.com/DistroAV/DistroAV/blob/04be005a085f4f6307f2a63ba612d0ad35b3aa9f/README.md)), and we could not read the NDI SDK license to confirm redistribution terms. F1.4 and F5.x import fidelity, GStreamer and plugin bundling, macOS signing and CI (dropped until an Apple account exists), and Windows antivirus friction all lack a phase. Our digest also notes that real NDI, real phones and any macOS or Linux behaviour are unmeasured, so Phase 2 "done" means "done in simulation".

## Better technical choices for capture, compositing, overlays, encoding and egress

### Stop treating slides as pixels to capture

The roadmap's F3.2 captures the presentation webview with `avfvideosrc`, `d3d12screencapturesrc` or `pipewiresrc`. The evidence argues for a different default, and this is our inference from the notes. Our importers already rasterise slides (PDFium to PNG, background images), so for imported decks the stream can receive frames directly: push the rendered slide as an `appsrc` still at program resolution and swap it on slide change. That needs no OS permission, works identically on all three platforms, has no self-capture or fullscreen-trap interaction, and is deterministic to the frame. Capture then becomes the fallback for content only a webview can draw (themed text, animated builds, F5.1 output), and there the notes recommend a dedicated program-render window decoupled from the projector window: FreeShow renders capture-only outputs at `bounds / scaleFactor` with a forced resolution so device pixels equal the configured size ([OutputBounds.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/output/helpers/OutputBounds.ts)), and our projector may be 4K, mirrored through a dongle, or a different aspect than a 1080p stream. (code for FreeShow's approach) Where capture is unavoidable, copy the OBS and Cap behaviours rather than the roadmap's element names: Windows Graphics Capture with a free-threaded frame pool of 2 buffers (Cap sizes it `clamp(ceil(fps/30*2),2,4)`), feature-probed border and cursor toggles, a `Closed` callback that raises `SourceLost`, adapter selection that skips software and virtual adapters, and a WARP fallback ([scap-direct3d lib.rs](https://github.com/CapSoftware/Cap/blob/d16fd199bbe8bd2a1c52fb19bcb3d383e9a2ff61/crates/scap-direct3d/src/lib.rs), [winrt-capture.cpp](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/libobs-winrt/winrt-capture.cpp)). (code) Hand frames to the compositor through a single-slot latest-frame-wins buffer, which in GStreamer terms is an `appsink` with `max-buffers=1 drop=true` or a leaky queue ([Sunshine thread_safe.h](https://github.com/LizardByte/Sunshine/blob/d0b4a88ef727f8dabf80cc970a14739b55c885de/src/thread_safe.h)). (code, mapping inferred) Store a small per-application compatibility list as data, as OBS does ([compatibility.json](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/plugins/win-capture/data/compatibility.json)). Do not build a native-PowerPoint remote-control path: OpenLP's COM, UNO and AppleScript controllers show the maintenance cost.

### Drive transitions from the frame clock with parked pads

For F3.3, adopt voctomix's mechanism and OBS's timing rule together. Pre-compute `frames = int(fps * ms / 1000)` values per pad property with the cosine ease `(1 - cos(pi x)) / 2`, write them as timestamped `GstController` control points against the pipeline clock, and apply them at a buffer boundary ([transitions.py](https://github.com/voc/voctomix/blob/173287ba60ce77c0595477f97c904f513de12c4d/vocto/transitions.py)). (code) A 500 to 750 ms fade at 30 fps is 15 to 23 points per property. Keep every source pad linked and park inactive ones at alpha 0 and zorder -1, which directly addresses the 53 to 60 ms gaps our digest recorded across runtime pad add and remove; reserve true add and remove for source-list changes. OBS derives transition progress from its render clock, blocks new transitions while one is active, supports a manual T-bar position, and allows per-scene transition overrides ([OBSBasic_Transitions.cpp](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/frontend/widgets/OBSBasic_Transitions.cpp)); all three are cheap to include. (code) CasparCG treats fade-through-black as its own `vfade` rather than a cross-fade, so F3.3's "fade to black" should be a dedicated transition, and its "side-wipe" should be named a push or slide (animating `xpos` and `width`) unless a shader is written, because neither voctomix nor CasparCG's push does a mask wipe. The unverified step is whether `GstController` bindings work on `d3d12compositor` and `glvideomixer` pads; voctomix proves them only on the CPU `compositor`, so spike that first and fall back to a Rust timer thread setting pad properties if needed. Expose both OBS-style counters (frames repeated to hold the timeline, frames dropped by a slow consumer) in the UI, and put per-source `fallbacksrc` or a "no signal" test pattern behind each camera so the mixer never starves ([avsource.py](https://github.com/voc/voctomix/blob/173287ba60ce77c0595477f97c904f513de12c4d/voctocore/lib/sources/avsource.py), [fallbackswitch](https://gitlab.freedesktop.org/gstreamer/gst-plugins-rs/-/blob/9cb42da34f16dd4e2679495a8f546518d863e57c/utils/fallbackswitch/src/fallbacksrc/imp.rs)). Keep queues small and make queues before encoders and network sinks `leaky=downstream`, as voctomix does for its recorder and SRT output rather than its 3 s default ([srtserver.py](https://github.com/voc/voctomix/blob/173287ba60ce77c0595477f97c904f513de12c4d/voctocore/lib/srtserver.py)). (code)

### Render overlays natively first, reserve webview and CEF for a spike

F3.4 is where the notes expose the most uncertainty, and the honest position is that no evidence shows a Tauri webview delivering alpha frames at video rate. CasparCG's answer is embedded CEF off-screen with a CPU copy and a JS contract; that is heavy to package. The cheaper tiers, in order, are a static PNG with an alpha fade driven by a linear control source (voctomix's `gdkpixbufoverlay` approach, [overlay.py](https://github.com/voc/voctomix/blob/173287ba60ce77c0595477f97c904f513de12c4d/voctocore/lib/overlay.py)), then Rust-rendered RGBA lower thirds pushed as frames (or the SVG and text overlay elements the notes list as GStreamer options), and only then a transparent webview or CEF. Adopt CasparCG's frame-delivery rules whichever route wins: a bounded drop-oldest queue of about four frames, and hold the last frame when no new paint arrives, because a static lower third produces none. (code, application inferred) Note that FreeShow's alpha path for OBS is NDI with an alpha-capable format ([Livestreaming docs](https://freeshow.app/docs/livestreaming)), so an NDI program output with key and fill is a related, separately valuable deliverable.

### Select encoders by running them

Three independent codebases converge on probing by encoding, and OBS notably does not. Sunshine keeps an ordered list, runs a real 1080p60 test encode per candidate, requires the first packet to be an IDR, caches the result, re-probes on display or GPU change, honours a named override, and skips probing when no display is active because of a Windows 11 24H2 DXGI problem ([video.cpp](https://github.com/LizardByte/Sunshine/blob/d0b4a88ef727f8dabf80cc970a14739b55c885de/src/video.cpp)). (code) webrtcsink validates each candidate by running a short pipeline and treating a bus error as rejection, sequentially "to avoid NVENC collisions" ([webrtcsink imp.rs](https://gitlab.freedesktop.org/gstreamer/gst-plugins-rs/-/blob/9cb42da34f16dd4e2679495a8f546518d863e57c/net/webrtc/src/webrtcsink/imp.rs)). (code) Cap reorders its list by detected GPU vendor on Windows (NVIDIA: nvenc, mf, qsv, amf, x264; AMD: amf first; Intel: qsv first) and falls back to software when the target frame rate exceeds 90% of an estimated hardware ceiling ([h264.rs](https://github.com/CapSoftware/Cap/blob/d16fd199bbe8bd2a1c52fb19bcb3d383e9a2ff61/crates/enc-ffmpeg/src/video/h264.rs)). (code) OBS probes out of process, so a crashing driver cannot take the app down ([nvenc-helpers.c](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/plugins/obs-nvenc/nvenc-helpers.c)). (code) For F4.1 this means: a fixed candidate table keyed by element name rather than registry rank (rank on Windows is unverified), a vendor-aware ordering, probing in a child process or a sacrificial pipeline, a TOML override with fallback, and `EncoderSelected` and `EncoderFailed` events on the bus carrying the reason. Reuse webrtcsink's per-encoder low-latency properties as data (NVENC `rc-mode=cbr-ld-hq` with `zerolatency`, QSV `low-latency` CBR, VA CBR, x264 `zerolatency` with `ultrafast`), and note it has no AMF or Media Foundation row, which we must write ourselves (inferred from its tables). The digest's summary of the F4.1 chain lists `vtenc_h264`, `mfh264enc`, `vaapih264enc` and `x264enc` and does not name NVENC, QSV or AMF; confirm the roadmap text, and review `vaapih264enc` against the newer `va` elements that webrtcsink's tables and the GStreamer 1.28 notes treat as current ([GStreamer 1.28](https://gstreamer.freedesktop.org/releases/1.28/)). Beat OBS by demoting automatically at start when an encoder fails, but treat a mid-stream swap as a reconnect with a visible notice, since it forces a new IDR and probably a new session.

### Make RTMP and SRT first-class egress, keep WHIP as one more transport

The roadmap says WHIP "replaces all RTMP egress", with Facebook and YouTube acceptance asserted "as of 2025" and unverified. The competitors disagree with that bet: ProPresenter, FreeShow, OBS and Mevo all rely on RTMP/RTMPS, OBS's WHIP output has no sender-side adaptation, and Enhanced RTMP is how HEVC and AV1 reach platforms ([flv-mux.c](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/plugins/obs-outputs/flv-mux.c)). (code) Our recommendation is to encode once to H.264, add an audio encode per transport family (Opus for WebRTC, AAC for RTMP; MediaMTX flags Opus-to-RTMP as needing a transcode), and branch the encoded stream through a `tee` with a `leaky=downstream` queue per destination into core GStreamer `rtmp2sink` and `srtsink` (the gst-plugins-rs tree has neither, and their Windows availability and quality need a `gst-inspect-1.0` check) plus `whipclientsink` where a platform accepts WHIP. Reconnect with OBS's schedule (2 s base, 1.5 exponent, jitter, 15 minute cap), or at least FreeShow's 1 to 15 s with forgiveness after 60 s alive ([obs-output.c](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/libobs/obs-output.c)). (code) For health, copy OBS's model: congestion as send-queue duration over a threshold (700 and 900 ms are tunables, not law), dropped-frame percentage, a four-state indicator and an explicit error enum ([OBSBasicStatusBar.cpp](https://github.com/obsproject/obs-studio/blob/95d5223b66da1c162acdb61c1bae2b9123a60f0e/frontend/widgets/OBSBasicStatusBar.cpp)). (code) Live bitrate changes are portable because webrtcsink whitelists `x264enc`, `nvh264enc`, `qsvh264enc` and `va*` for live bitrate property updates (each with its own unit), so F6.2's adaptive bitrate for RTMP and SRT is send-queue-driven control we write ourselves, while GCC through `rtpgccbwe` serves WHIP only, and whether `rtpgccbwe` ships in the Windows GStreamer installer is unchecked. This argues for pulling basic congestion handling into Phase 4. Treat MediaMTX as an optional MIT sidecar for runtime-editable fan-out, local fMP4 recording and `srt_conns_*` metrics when destinations exceed about three; the cost is another signed executable per OS, default listeners that must be rebound to localhost, process supervision and thin per-destination health. It also could replace our F2.4 phone ingest server, but our in-process path already passed a real WebRTC loopback test, so keep ours and borrow MediaMTX's response headers (`Location`, `ETag`, `Link`, `Accept-Patch`) and its `PATCH` trickle handling for phones that require it ([http_server.go](https://github.com/bluenviron/mediamtx/blob/0cf5719cf504ddc046bb4df3636fdb6d942c20a1/internal/servers/webrtc/http_server.go)). (code, comparison against our code not performed)

## Competitor features our roadmap lacks, ranked by worth

The roadmap's silence is not proof of intent, but the digest found no feature or acceptance criterion for any of the following. **Audio** is the largest hole: OBS runs an audio thread with 1024-sample ticks and per-source filters ([backend-design](https://raw.githubusercontent.com/obsproject/obs-studio/master/docs/sphinx/backend-design.rst)), FreeShow ships a Web Audio mixer with routing and effects forwarded to RTMP, NDI and SDI, and Mevo Studio markets an audio mixer (docs). A streaming product with no audio acceptance criterion cannot replace Mevo Studio. **Local recording** exists everywhere: OBS Hybrid MP4/MOV (default in 32.0, [release](https://github.com/obsproject/obs-studio/releases/tag/32.0.0)), ProPresenter 7.1, FreeShow, MediaMTX fMP4 and Mevo's per-camera microSD ISO. **A control API plus a Companion module** is the integration every competitor ships, and the notes give a template: a thin WebSocket and HTTP bridge subscribed to the `AppEvent` bus (preserving the bus-only invariant), scoped bearer tokens kept in the keychain (Companion's REST API uses `read`, `write`, `execute` and `admin` scopes, [RestApiAuth.ts](https://github.com/bitfocus/companion/blob/bef66ef26ee1a1f90864c914ec5aab1401969d5d/companion/lib/Service/RestApi/RestApiAuth.ts)), state pushed immediately on connect as OpenLP's socket does, a `get_*` query convention like FreeShow's, and a first-party TypeScript Companion module exposing boolean feedbacks (presenting, blackout, stream live, source lost) and JSON-typed variables. Let Companion own Stream Deck hardware; a Satellite client is low value. Where we beat FreeShow is TLS-capable scoped auth and Rust-side execution. **A stage and confidence display** (current and next slide, notes, clock) exists in ProPresenter, FreeShow and OpenLP and is nearly free for us since we already hold that data; FreeShow's version caps at 10 clients and resets all of them on overflow, an easy defect to avoid. **NDI program output with key and fill** is cheap because `ndisink` exists in gst-plugin-ndi (default feature), and ProPresenter limits alpha to NDI and capable SDI hardware. **Countdown timers** are missing from OpenLP entirely and cheap for us to add on the existing timer machine. A lower-priority group is **PTZ control** (none in the roadmap; DistroAV polls PTZ and web-control URLs), **projector control over PJLink** (implement from the public spec, never from OpenLP's code), and **Planning Center import** (keychain-bound credentials).

**Songs, lyrics and scripture** are a scope decision before a build item. They are ProPresenter's and FreeShow's core and the reason a worship team keeps ProPresenter; OpenLP's model (verse tags plus a verse-order string, OpenLyrics, ChordPro, CCLI `.usr`/`.txt`, a passive usage log exported as CSV) is the minimal credible set ([songs db.py](https://gitlab.com/openlp/openlp/-/blob/438eb25a7cb969079efbb4bc716b7b42b8d39c5d/openlp/plugins/songs/lib/db.py)). (code) The roadmap names no audience; its slide classes ("keynote-cam", "presenter-wide") imply talks and events, and the digest read the absence of lyrics as evidence against a worship-first target. If that is right, say plainly that "no ProPresenter dependency" means decks, not songs, and keep the import adapters as a migration aid. FreeShow's local speech-to-text scripture follow and LLM slide generation are differentiators we should not chase.

## Corrections to our own assumptions

The Rust toolchain line in CLAUDE.md (1.78) is not compatible with anything we might pull in from the reference set: gst-plugins-rs declares `rust-version = "1.92"` on edition 2024 ([Cargo.toml](https://gitlab.freedesktop.org/gstreamer/gst-plugins-rs/-/blob/9cb42da34f16dd4e2679495a8f546518d863e57c/Cargo.toml)), and Cap pins `1.88.0` ([rust-toolchain.toml](https://github.com/CapSoftware/Cap/blob/d16fd199bbe8bd2a1c52fb19bcb3d383e9a2ff61/rust-toolchain.toml)) (code). This matters only if we build those crates or vendor Cap's code in-tree, since loading gst-plugins-rs as a binary plugin carries no toolchain requirement, but the stack row should be re-verified against `rustc --version` and the lockfile anyway, because it also looks stale next to Tauri 2.12 and axum 0.8 (inferred). The digest also notes that the GStreamer version named in discussion ("1.28.3") does not appear in CLAUDE.md and the roadmap targets 1.26.x; the 1.28 release adds `webrtcsink` renegotiation, VA encoder support and a WHEP signaller ([notes](https://gstreamer.freedesktop.org/releases/1.28/)), so decide the baseline deliberately, bearing in mind that mirrors disagree on the latest 1.28 point release (1.28.4 versus 1.28.6). (docs)

The scap licensing nuance is real. Cap's root LICENSE puts only the `cap-camera*` and `scap-*` crate families under MIT and everything else under AGPL-3.0 ([LICENSE](https://github.com/CapSoftware/Cap/blob/d16fd199bbe8bd2a1c52fb19bcb3d383e9a2ff61/LICENSE)). Crate-level `license = "MIT"` appears on `scap-direct3d`, `scap-screencapturekit`, `scap-ffmpeg`, `scap-cpal` and the camera crates, but is absent from `scap-targets` (covered only by the family wording) and from `cap-d3d-adapter`, whose name is outside either MIT family and so falls under the root AGPL clause. `scap-direct3d` depends on `cap-d3d-adapter` on Windows and calls it from `create_d3d_device_with_warp_fallback`. (code) The practical options are to reimplement the roughly 60 lines of DXGI adapter enumeration (skip software and virtual adapters, honour a preferred LUID, fall back to WARP) or use the `windows` crate directly; if `scap-*` is vendored, keep the MIT text and headers and confirm `scap-targets` with the maintainer. The notes also show the crates as path dependencies only, built on git forks of `cidre`, `nokhwa` and `ffmpeg-next`, so reuse means vendoring pinned revisions, not a crates.io dependency. (code, "not on crates.io" is as far as the repo shows) Cap's capability file (`windows: ["*"]` with `fs:write-all`) must not be copied; it violates our capability-minimalism invariant.

The goal statement is internally inconsistent. CLAUDE.md and the brief say zero dependency on Mevo Studio and ProPresenter "by Phase 5", but the digest reports the roadmap's own Phase Gate table retiring Mevo Studio at Phase 4 (streaming only), ProPresenter at Phase 5 as "(optional)", and "all external tools optional" only at Phase 6. Reconciling it needs three further admissions. First, Mevo Studio is a phone app, so retiring it means replacing the phone as encoder and mixer; the cameras themselves remain external, their proprietary transport is unreachable, and exposure, pan-and-crop and camera setup over Bluetooth are lost without Studio. Second, "zero dependency" still leaves the NDI runtime, the GStreamer plugin set (with x264 and OpenH264 licensing noted in the digest), the OS keychain and signing infrastructure as external. Third, F5.4 (a ProPresenter bridge) is a coexistence feature that sits awkwardly in a phase named independence; ProPresenter's documented API on port 50000 means it can be built from the published spec rather than reverse engineering ([API](https://renewedvision.com/propresenter/api/)). (docs) Pick one phase number, define "independence" as an operational test (a full service run, streamed and recorded, with Mevo Studio and ProPresenter uninstalled, using NDI, SRT or UVC cameras), and write the dependency exceptions down.

One smaller assumption deserves checking: the notes show that NDI "New Format" detection needs no SDK signal. Both gst `ndisrc`/`ndisrcdemux` and DistroAV compare the incoming frame's format with the last seen and renegotiate, and neither branches on the SDK's status-change frame types ([ndisrcdemux imp.rs](https://gitlab.freedesktop.org/gstreamer/gst-plugins-rs/-/blob/9cb42da34f16dd4e2679495a8f546518d863e57c/net/ndi/src/ndisrcdemux/imp.rs)). Our `advertises_new_format` flag, always false from the GStreamer provider, can be replaced by comparing width, height, frame rate and FourCC. (code, inferred application) Also expose NDI `extra_ips` and groups in config, since discovery uses mDNS and does not cross subnets, a gap in gst's provider.

## Licensing: study the GPL tools, reuse the MIT and MPL ones

Everything that should only be read is copyleft: OBS (GPL-2.0-or-later, `COPYING` plus source headers), FreeShow (GPL-3.0, `package.json` and `LICENSE`), CasparCG (GPL-3.0), OpenLP (GPL-3.0-or-later in every source header), Sunshine (GPL-3.0), DistroAV (GPL-2.0), obs-websocket (GPL-2.0 per the web layer; its source was an empty submodule and could not be read), and Cap outside its MIT crates (AGPL-3.0). Copying or closely translating code, shaders, compatibility-list entries, importer mappings or theme defaults from these into a distributed app would impose their license on the combined work. Reimplementing from behaviour is safe in the ordinary reading: thresholds such as OBS's 700 and 900 ms, file-format structure (OPC for PPTX, OpenLyrics, ChordPro, the CCLI formats, PJLink) and protocol behaviour are facts or tunables, not code, though this is not legal advice and a review is warranted before commercial distribution. Two traps are worth naming. OpenLP's importers are GPL even where the underlying formats are public, so implement from the format specs and our own fixtures. FreeShow bundles ProPresenter 7 `.proto` schemas derived from community reverse engineering ([import.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/data/import.ts)); the provenance and license of those schemas is unaudited, so do not copy them. Running a GPL program such as CasparCG as a separate process would keep our code independent, but CasparCG needs an OpenGL 4.5 GPU and CEF and is not recommended as a dependency.

The usable set is smaller and sufficient. voctomix (MIT, with the 2014-2016 c3voc notice) lets us port the control-source pattern outright with attribution. MediaMTX (MIT) can ship as a sidecar if we include its notice and its dependencies' notices. Companion's core (MIT, with a contributor agreement that grants Bitfocus a licence over contributions) and its `satellite-protocol` conformance corpus are usable with notices, though that package's own licence field was not inspected. gst-plugins-rs is MPL-2.0, which is file-level copyleft: loading its plugin binaries imposes nothing on us, while copying source files requires MPL compliance for those files. Cap's `scap-*` crates are usable under the caveats in the previous section. LiveKit server is Apache-2.0 but was only listed as a possible Egress reference. NDI sits outside all of this: the SDK headers vendored by DistroAV carry an MIT notice "ONLY and not to the SDK as a whole", and the NDI SDK License Agreement PDF could not be read, so redistribution of the runtime library inside our installer is unverified; both DistroAV and gst-plugin-ndi avoid the question by requiring a user-installed runtime, and we should do the same until the agreement is read ([NDI header](https://github.com/DistroAV/DistroAV/blob/04be005a085f4f6307f2a63ba612d0ad35b3aa9f/lib/ndi/Processing.NDI.Lib.h)). The digest also flags x264 (GPL) and OpenH264 as bundling questions for the GStreamer set, which no note audited. Companion's module SDK and generic modules live in separate repositories with unverified licences. ProPresenter and Mevo are proprietary, and we are replicating features rather than formats, so interoperability should be limited to documented APIs, published file import and standard camera outputs.

## Conclusion

The notes change what the roadmap is really about. It is framed as three tools to replace, but the evidence shows two of the hardest problems (presenting slides into a video pipeline and rendering overlays) are best solved by not capturing a screen at all, while the dull ones (audio, recording, an authenticated control API, a camera ingest that works with Mevo models lacking NDI) are what operators will notice missing on day one. FreeShow proves the market wants one product that does everything and also proves how quickly a webview-and-readback architecture hits a bandwidth wall; our GPU-resident GStreamer path avoids that wall, but only if we keep slides, overlays and audio off the readback path from the start.

The second implication concerns honesty about independence. A team can honestly claim independence from Mevo Studio and ProPresenter only against an operational test, and "zero dependency" will always carry named exceptions: the NDI runtime, the GStreamer plugin set and the cameras themselves. Writing those exceptions down now, and fixing the small factual errors (toolchain version, scap's licence boundary, the Phase 4/5/6 gate), costs little and prevents the larger mistake of discovering them at packaging time.
