## 1. Companion: how a third-party app integrates (module SDK, satellite, generic HTTP/OSC/TCP/WS)

### Takeaway
There are three integration routes. (a) The app exposes an HTTP/OSC/WebSocket API and users drive it from generic connections. (b) The app ships a real Companion module (Node/TypeScript process using `@companion-module/base`) that declares actions, feedbacks, variables and presets. (c) The app acts as a Satellite client or surface. For a presentation tool the module route (b) is the only one that gives proper feedbacks and variables. Route (a) is the cheap base layer and can be built first.

### Cited findings
- **Inbound control surfaces of Companion itself [V]**: it serves HTTP (default port 8000, `docs/user-guide/1_getting-started/start-the-server.md`), OSC (default 12321, `docs/user-guide/5_remote-control/osc-control.md`), TCP/UDP text commands (`tcp-udp.md`), Satellite TCP 16622 and WebSocket 16623 (`docs/user-guide/5_remote-control/satellite.md`, `companion/lib/Service/SatelliteTcp.ts` sets `this.port = 16622`), plus ArtNet, Ember+, Rosstalk and a Prometheus endpoint. Code is in `companion/lib/Service/*` (`HttpApi.ts`, `OscApi.ts`, `Tcp.ts`, `Udp.ts`, `SatelliteWebsocket.ts`, `Artnet.ts`, `EmberPlus.ts`, `Rosstalk.ts`). These let other software press Companion buttons. They are not the way Companion reaches our app.
- **Companion to our app direction [V]**: only "connections". A connection is an instance of a module, and each runs in its own child process. `companion/lib/Instance/Connection/ChildHandlerApi.ts` and `IpcTypesNew.ts` define a host/module IPC protocol with `ModuleToHostEventsNew` and `HostToModuleEventsNew`.
  - Module to host: `register`, `log-message`, `set-status`, `setActionDefinitions`, `setFeedbackDefinitions`, `setVariableDefinitions`, `setPresetDefinitions`, `setCompositeElementDefinitions`, `setVariableValues`, `updateFeedbackValues`, `saveConfig`, `send-osc`, `recordAction`.
  - Host to module: `init` (label, config, secrets), `destroy`, `updateConfig`, `updateFeedbacks`, `updateActions`, `upgradeActions`, `upgradeFeedbacks`, `executeAction`, `getConfigFields`, `handleHttpRequest`, `learnAction`, `learnFeedback`, `startStopRecordActions`.
  - The SDK is the external npm packages `@companion-module/base` and `@companion-module/host` (imported in `IpcTypesNew.ts`). The SDK source is NOT in this clone. The author-facing API (class `InstanceBase`, `runEntrypoint`) is therefore [I] from these IPC types.
- **Module loading [V]**: `companion/lib/Instance/ModuleScanner.ts` reads a `companion/manifest.json` per module (`validateManifest` from `@companion-module/base/manifest`) and distinguishes "connection v2", legacy and surface manifests. `shared-lib/lib/Model/ModuleManifest.ts` shows the manifest carries a `runtime` block. `companion/lib/Instance/Connection/ApiVersions.ts` gates behaviour on module API semver (>=2.0.0 uses the new child handler). Modules are downloadable plugins since 4.0 (`docs/user-guide/3_config/connections.md`). A dev folder `module-local-dev/` exists (only a `package.json`, no README).
- **Third-party module via manifest, no Companion code changes [V]**: connections are discovered from module folders, so we could publish a module independently. Bitfocus's own generic modules (generic-http etc.) are separate repos. Only an integration test references `generic-http` v3.1.0 (`companion/test/integration/GenericHttpVariables.test.ts`), and it shows the module takes custom-variable fields for response data and status. The generic-osc/tcp/websocket modules are not in this clone, so their feature sets are not verified here.
- **Entity model for actions and feedbacks [V]**: `shared-lib/lib/Model/EntityDefinitionModel.ts` (`ClientEntityDefinition`) describes an entity with `entityType`, `label`, `options` (input fields), `feedbackType`, `hasLearn`, `actionHasResult`, `optionsSupportExpressions`, etc. `shared-lib/lib/Model/EntityModel.ts` has `FeedbackEntitySubType = boolean | advanced | value | style-override`. Boolean feedbacks give true/false that restyles a button. Advanced feedbacks return style objects. Value feedbacks return a value for expressions.
- **Variables [V]**: `shared-lib/lib/Model/Variables.ts`: `VariableDefinition {name, description}` and `VariableValue = JsonValue | undefined` (not string-only). Module variables are read over HTTP with `GET /api/variable/<ConnectionLabel>/<name>/value` (`docs/user-guide/5_remote-control/http-remote-control.md`; `companion/lib/Service/HttpApi.ts`). Variable values are pushed from the module in batches (`Connection/VariableValueBatcher.ts`). The `$(label:name)` reference syntax is from general Companion knowledge, not re-checked in this clone [I].
- **Presets [V]**: `shared-lib/lib/Model/Presets.ts` has `PresetDefinition {id, name, type:'button', model: LayeredButtonModel, presetExtraFeedbacks, keywords}`, grouped into `UIPresetSection` then `UIPresetGroup` (`simple` or `template` with `templateVariableName` and `templateValues`). Presets pre-wire a button's style, steps (down/up actions) and feedbacks. Template presets give one preset per list item (for example one button per slide or scene).
- **Satellite protocol [V]**: line-based text protocol over TCP 16622 or WebSocket 16623. Commands handled in `companion/lib/Service/Satellite/SatelliteApi.ts`: `ADD-DEVICE`, `REMOVE-DEVICE`, `KEY-PRESS`, `KEY-ROTATE`, `SET-VARIABLE-VALUE`, `PINCODE-KEY`, `ADD-SUB`, `REMOVE-SUB`, `SUB-PRESS`, `SUB-ROTATE`, `FIRMWARE-UPDATE-INFO`, `CHANGE-PAGE`, `DEVICE-APPEARANCE`, `PING`, `PONG`, `QUIT`. The server sends `BEGIN` (CompanionVersion, ApiVersion) then `CAPS` (SUBSCRIPTIONS, NONSQUARE, BITMAP_FORMATS, ROTARY_AMOUNT). Format is `COMMAND [DEVICEID] KEY=value KEY="quoted value"` with valueless flags (`satellite-protocol/README.md`, `lib/codec.ts`). Lines are capped at 2 MB (`MAX_LINE_LENGTH`). API version 1.15.0 (`satellite-protocol/lib/constants.ts` changelog comment). The `ADD-SUB` button-subscription API (v1.10.0+) lets a client subscribe to a specific button's rendered state and press it, without owning a grid surface. The package `@companion-app/satellite-protocol` (`satellite-protocol/`) is zod-only and ships `assets/satellite-protocol-corpus.json` conformance cases for other languages. A Rust client could be validated against it.
- **Stream Deck hardware [V/I]**: Companion core does not link Elgato USB code directly in the files read. `companion/package.json` depends on `@companion-surface/host`, and docs say surface support has been delivered as installable "surface modules" since 4.3 (`docs/user-guide/7_surfaces/index.md`). `companion/lib/Instance/Surface/*` is the host side and `companion/lib/Surface/IP/Satellite.ts` and `ElgatoEmulator.ts` handle network surfaces. Which USB library the Stream Deck surface module uses is NOT visible in this clone [gap]. Companion's own docs say the remote-surface path is the separate "Companion Satellite" app.
- **REST API 5.1 [V]**: `companion/lib/Service/RestApi/*` provides an OpenAPI 3.0 document (`openapi.ts`) with Swagger UI (`SwaggerUi.ts`) and bearer tokens with scopes `read`/`write`/`execute`/`admin` (`RestApiAuth.ts`). It manages connections, surfaces and config.
- **Companion's control surface in HTTP [V]**: `POST /api/location/<page>/<row>/<column>/press|down|up|rotate-left|rotate-right|step`, `POST .../style` with `{text,color,bgcolor,size}`, `POST|GET /api/custom-variable/<name>/value`, `GET /api/variable/<label>/<name>/value`, `GET /api/connections` (`docs/.../http-remote-control.md`, `HttpApi.ts`). OSC uses the same path vocabulary (`/location/1/0/5/press`, `OscApi.ts`).
- **Module to external HTTP [V]**: `handleHttpRequest` exists in `HostToModuleEventsNew`, so a module can receive inbound webhooks routed through Companion's HTTP port. Useful if we want push events to arrive at Companion without polling.

### Inferences
- **Minimum viable integration**: a localhost HTTP + WebSocket (or OSC) API on the app: `POST /api/slide/next|prev|goto/<n>`, `POST /api/present/start|stop`, `POST /api/blackout`, `GET /api/state`, and a WS stream of state changes. Users wire it in Companion with generic HTTP buttons and generic WebSocket modules. State into Companion is the weak point: generic modules poll or parse, so there are no proper boolean feedbacks (such as "slide 3 is live") without a real module. [I, since the generic modules' code is not in this clone]
- **Recommended**: ship a first-party Companion module (TypeScript, own repo, MIT-compatible) that speaks to our WS API. Expose:
  - Actions: next/prev/goto slide, start/stop present, blackout/unblackout, scene cut, camera select, start/stop stream, timer start/stop/reset, push media.
  - Feedbacks (boolean): presenting, blackout, stream live, slide-is-N, source-lost, timer-running, deck-loaded. Value/advanced feedbacks: slide thumbnail, timer remaining.
  - Variables (JSON-typed, `name`+`description`): `slide_index`, `slide_total`, `slide_title`, `next_slide_title`, `notes`, `timer_remaining`, `timer_elapsed`, `stream_state`, `deck_name`, `active_scene`, `source_<n>_state`, `fps`, `bitrate`.
  - Presets: transport buttons plus template presets per scene/camera, using `templateValues`.
- Our existing `AppEvent` bus maps naturally: `SlideUpdate`, `DeckEnd`, `SourceLost`, etc. become variable/feedback updates, so the API can be a thin WS bridge from the bus (keeps the event-bus-only invariant). The API server must be an additive subsystem; keep the bearer token in the OS keychain (as already done for WHIP). Companion's scoped bearer tokens (`RestApiAuth.ts`) are a good model.
- A Satellite client is only worth doing if we want a Stream Deck-style button grid inside our own UI or on a phone/tablet. For hardware, let Companion own the Stream Deck.

### Gaps
- Module SDK source (`@companion-module/base`, `@companion-surface/*`) and the generic-http/osc/tcp/websocket modules are not in the clone, so authoring API details and the polling/feedback features of the generic modules are unverified. The satellite developer doc is only linked (`https://companion.free/for-developers/Satellite-API`), not cloned. No code was run, so wire behaviour is unconfirmed beyond source and tests.
- The USB library used for Stream Deck hardware is not visible in the clone.

## 2. OpenLP: plugins, service model, presentation display, API, importers, CCLI

### Takeaway
OpenLP is a Qt/Python monolith. Everything (songs, bibles, custom slides, images, media, presentations, alerts, planning center, OBS) is a `Plugin` that produces a `ServiceItem`. A service is an ordered list of those, saved as a zip with a JSON manifest. Its output is text-to-HTML slides on a QtWebEngine page, and PowerPoint/Impress/Keynote are driven as external processes. The presentation story is the fragile part. The data model (songs, tags, verse order, usage) is the part worth studying.

### Cited findings
- **Plugin architecture [V]**: `openlp/core/lib/plugin.py` defines `Plugin` with hooks `check_pre_conditions`, `create_media_manager_item`, `add_import_menu_item`, `add_export_menu_item`, `create_settings_tab`, `add_to_menu`, `handle_event`, plus `weight` and `PluginStatus` (toggled via settings key `{name}/status`). `core/lib/pluginmanager.py` globs `plugins/*/[!.]*plugin.py` (the app dir and a community data-dir) via `extension_loader`. Plugins present in `openlp/plugins/`: alerts, bibles, custom, images, media, obs_studio, planningcenter, presentations, songs, songusage. Each plugin has its own SQLite DB where it needs one (SQLAlchemy, e.g. `plugins/songs/lib/db.py`).
- **Service item / plan model [V]**: `openlp/core/lib/serviceitem.py` `ServiceItem` has `title`, `slides`, `theme`, `notes`, `capabilities`, `service_item_type` (`ServiceItemType` enum Text=1, Image=2, Command=3 in `core/common/enum.py`), `footer`/`raw_footer`, `audit`, `from_plugin`, `start_time`/`end_time`, `background_audio`, `timed_slide_interval` / `auto_play_slides_once|loop`, `sha256_file_hash`. Methods: `add_from_text`, `add_from_image`, `add_from_command` (presentations), `get_service_repr`, `set_from_service`, `to_dict`. Capabilities (`ItemCapabilities` in `core/lib/__init__.py`) drive which controls appear (for example `HasThumbnails`, `HasNotes`, `ProvidesOwnTheme`, `CanStream`, `HasBackgroundVideo`). Text is rendered by OpenLP, Image is full-frame picture, Command is "handled by an external app" (presentations).
- **Service file [V]**: `core/ui/servicemanager.py` `save_file`/`load_file`: zip containing `service_data.osj` (JSON via `OpenLPJSONEncoder`), with the actual media files stored by hash (`{sha256}{ext}`, see `get_service_repr`). `.osz` = packaged with files, `.oszl` = "lite" (references only; `service_has_all_original_files` check).
- **Theme model [V]**: `core/lib/theme.py` `Theme` loads defaults from `core/lib/json/theme.json` and flattens the nested JSON into attributes (`expand_json`). Enums: `BackgroundType`, `BackgroundGradientType`, `TransitionType`, `TransitionSpeed`, `TransitionDirection`, `HorizontalType`, `VerticalType`. Theme level (`ThemeLevel`: Global=1, Service=2, Song=3 in `core/common/__init__.py`) decides precedence: `ServiceItem.get_theme_data` takes global, then the service theme if the item is in a service, then the per-song theme if the level is Song.
- **Display path [V]**: `core/display/window.py` `DisplayWindow` hosts a QtWebEngine view with `core/display/html/display.html` + `display.js` + `reveal.js` + `textFit.js`. Python calls JS via `run_in_display`, e.g. `load_verses`, `load_images`, `set_theme`, `go_to_slide`, `alert`, `hide_display(HideMode)`. A QWebChannel `DisplayWatcher` sends events back. Slide text, footer and chords are rendered by `core/display/render.py` (`render_tags`, `remove_tags`, `render_chords_for_printing`). Screens: `core/display/screens.py` `ScreenList`.
- **PowerPoint (Windows) [V]**: `plugins/presentations/lib/powerpointcontroller.py` uses `win32com.client.Dispatch('PowerPoint.Application')`. In `export_presentation_data` it runs `slide.Export(...png, w, 360)` per slide for thumbnails, collects title and notes text, and builds an `index_map` that skips hidden slides. It drives `SlideShowSettings.Run()`, `SlideShowWindow.View.Next()/Previous()/GotoSlide()/GotoClick()`, and blank via `View.State = 3`. Supported: ppt, pps, pptx, ppsx, pptm (and odp). Hacks visible in code: it edits a PowerPoint registry key to choose the monitor (`modify_powerpoint_display_monitor`), repositions the window by DPI (`adjust_powerpoint_window_position`), enumerates windows to close a "ghost window" (`close_powerpoint_ghost_window`), and works around PowerPoint stealing focus on multi-monitor setups. Other limits seen: `pywintypes.com_error` handling everywhere, cloud documents (`is_in_cloud`), animation click counting (`GetClickCount`/`GetClickIndex` in `next_step`), and state `5` ("done") where `SlideIndex` is unavailable.
- **LibreOffice Impress [V]**: `impresscontroller.py` uses UNO (`import uno`, `get_uno_command()`, `get_uno_instance`, desktop via `com.sun.star.frame.Desktop`), exports thumbnails with `impress_png_Export`, and has a `SlideShowListener` (XSlideShowListener) for slide events on non-Windows. `start_presentation` waits up to 15 s for the controller. macOS uses a separate server process (`libreofficeserver.py`, pipe `openlp_maclo`; `maclocontroller.py`), Keynote uses AppleScript (`keynotecontroller.py`, `applescriptbasecontroller.py`) and macOS PowerPoint uses AppleScript (`powerpointmaccontroller.py`). Impress also advertises ppt/pps/pptx/ppsx/pptm (`impresscontroller.py` `also_supports`).
- **PDF [V]**: `pdfcontroller.py` renders each page to PNG with **Qt's `QPdfDocument`**, not MuPDF or Ghostscript. A grep of `openlp/` finds no mupdf/ghostscript use at this commit. The `PdfDocument` docstring says it is "not actually used to present the PDF": pages become an image service item. Pages are scaled to the screen geometry and cached as `mainslide001.png`; a white background is painted manually. So PDF has no notes or animations. The brief's "mupdf/ghostscript" is not supported at this commit (may reflect older OpenLP versions).
- **Presentation controller abstraction [V]**: `presentationcontroller.py` `PresentationDocument` hooks: `load_presentation`, `start_presentation`, `stop_presentation`, `blank_screen`/`unblank_screen`/`is_blank`, `get_slide_number`/`get_slide_count`, `goto_slide`, `next_step`/`previous_step`, `get_thumbnail_path`, `get_slide_text`/`get_slide_notes`/`get_titles_and_notes`, `attempt_screenshot`, `poll_slidenumber`. `PresentationController` has `supports`/`also_supports` extension lists and `check_available`/`start_process`/`kill`. This hook list is a good checklist for a presenter backend trait of our own.
- **HTTP API [V]**: Flask app served by waitress (`core/api/http/server.py`), default ports 4316 (HTTP) and 4317 (WebSocket), `api/user id`/`api/password`/`api/authentication enabled` (`core/common/settings.py`; defaults `openlp`/`password`, auth disabled). Blueprints at `/api/v2/` (`core/api/versions/v2/__init__.py`):
  - `controller/`: `live-items`, `live-item`, `show` (POST `{id}`), `progress`, `theme-level`, `themes`, `live-theme`, `theme`, `clear/<controller>`.
  - `core/`: `display` (POST), `plugins`, `shortcuts`, `system`, `language`, `login`, `live-image`.
  - `service/`: `items`, `show/<item_id>`, `progress`, `new`, `delete_item`.
  - `plugins/<plugin>/`: `search`, `add`, `live`, `search-options`, `alerts` (POST), songs `transpose-live-item/<n>`.
  Mutating routes use `@login_required` (`core/api/lib.py`; token via the `authentication_token` registry value).
- **WebSocket [V]**: `core/api/websockets.py` has two kinds of connection. The default path returns a state blob. Paths starting `/messages` get typed `WebSocketMessage{plugin,key,value}` pushes (a code comment says state-based sockets are to be removed in favour of messages). State blob (`core/api/websocketspoll.py` `create_state`): `counter` (slide count), `service` id, `slide` (selected row), `item` (unique id), `blank`, `theme`, `display`, `twelve`, `version: 3`, `isSecure`, `chordNotation`. It is rebuilt whenever the live controller or service manager signals a change, and a new client gets the current state immediately on connect.
- **Stage and remote views [V]**: `core/api/main.py` serves `/stage/<name>/` HTML and assets from a `stages` data dir; `core/api/deploy.py` downloads the web remote zip from `https://get.openlp.org/remote/` into `remotes/`. The stage and remote web UIs are therefore NOT in this repo. Their exact data use is unverified; they presumably consume the same `/api/v2` and WS endpoints [I].
- **Songs [V]**: `plugins/songs/lib/db.py` `Song` (title, alternate_title, lyrics as OpenLyrics-style XML text, verse_order, copyright, comments, `ccli_number`, theme_name, search_title/search_lyrics, create_date, last_modified, `is_favourite`, `temporary`), many-to-many to `Author` (with `author_type`), `SongBook` + `SongBookEntry` (entry number per book), `Topic`, `MediaFile` (linked audio/video). `plugins/songs/lib/openlyricsxml.py` handles OpenLyrics (header documents version 0.7). Verse order is a string that drives how slides are built.
- **Song importers [V]** (`plugins/songs/lib/importers/`): cclifile (CCLI `.usr` and `.txt`), chordpro, datasoul, dreambeam, easyslides, easyworship, foilpresenter, liveworship, lyrix, mediashout, openlp, openlyrics, openoffice, opensong, opspro, powerpraise, powersong, presentationmanager, propresenter, singingthefaith, songbeamer, songpro, songshowplus, songsoffellowship, sundayplus, videopsalm, wordsofworship, worshipassistant, worshipcenterpro, zionworx. All build on `songimport.py` `SongImport`. Also `songselect.py` and `openlyricsexport.py`.
- **Bibles [V]**: `plugins/bibles/lib/db.py` per-translation SQLite (`BibleMeta`, `Book`, `Verse`), `manager.py` `BibleManager` with `parse_ref`, `get_verses`, `verse_search`, `process_verse_range`. Importers: csv, http (online), opensong, osis, sword, wordproject, zefania.
- **Custom slides, images, media, alerts [V]**: custom slides (`plugins/custom/lib/customxmlhandler.py`), images (`plugins/images/`), media (`plugins/media/`), alerts (`plugins/alerts/lib/alertsmanager.py` `alert_text`/`display_alert`, with timeout/scroll/repeat settings in `alertstab.py`; also reachable via `POST /api/v2/plugins/alerts`).
- **CCLI [V]**: three separate things. (1) Song field `ccli_number` plus CCLI-number search (`songs/lib/mediaitem.py`). (2) The `songusage` plugin logs projected songs into `SongUsageItem` (date, time, title, authors, copyright, `ccl_number`, plugin_name, source; `plugins/songusage/lib/db.py`) and exports a quoted CSV with columns date, time, title, copyright, ccli, authors, plugin name, source (`plugins/songusage/forms/songusagedetailform.py`). The operator uploads that CSV to CCLI manually. (3) SongSelect integration (`songselect.py`) drives an embedded browser through `profile.ccli.com` sign-in and `songselect.ccli.com` search to download songs. No direct usage-reporting API client was found.
- **Planning Center [V]**: `plugins/planningcenter/lib/planningcenter_api.py` `PlanningCenterAPI` (basic auth with application id and secret): `get_service_type_list`, `get_plan_list`, `get_items_dict`. It imports a plan into a service. Only external planning integration, one-way.
- **Projector control [V]**: `core/projectors/pjlink.py` and `pjlinkcommands.py` implement PJLink network projector control.
- **No countdown timer found [V]**: grep for "countdown" across `openlp/` returned nothing.
- **Hide modes [V]**: blank / theme / desktop (`HideMode` in `core/ui`; surfaced as `blank/theme/display` in the WS state). End-of-item behaviour is configurable (`SlideLimits` in `core/common/__init__.py`).

### Inferences (what they got right and wrong for operators)
- **Right**: a single `ServiceItem` abstraction lets songs, scripture, slides, media and presentations sit in one ordered list; capabilities drive the UI. Three-level theming (global / service / song). Verse tags plus verse order mean a song is entered once and sequenced per service. A stored service is a portable zip with hashed assets. WS state push with immediate state on connect makes remotes easy. The plugin boundary isolates importers. Song usage logging is passive (no operator step per song).
- **Wrong or costly**: presentations rely on controlling someone else's app (COM, UNO, AppleScript) with many focus/ghost-window/registry hacks, and controller code is duplicated across Windows, mac and LibreOffice. PDF is flattened to images with no notes; PowerPoint hidden slides and animations need special handling (`index_map`, click counting). Stage and remote UIs are a separate download. Auth is a simple user/password with a default `openlp`/`password`, disabled by default. No countdown timer. CCLI reporting is a manual CSV. GPL-3 Python/Qt code cannot be reused in a non-GPL project.
- **For us [I]**: our existing PPTX/PDF importers render slides ourselves, which avoids COM/UNO fragility; keep that. The cost is fidelity (animations/transitions are not reproduced). OpenLP's route keeps full PowerPoint fidelity at the price of fragility. Make that trade-off explicit to users.

### Gaps
- The web remote and stage view source, and the exact stage data (current/next slide, clock), are not in the clone.
- Presentation behaviour was read statically, so the real-world failure rate of each controller is unverified. Mac/Linux paths untested.
- No MuPDF/Ghostscript code was found at this commit; if the brief meant an older version, that needs a different clone.
- MIDI/OSC handling in OpenLP was not found and not searched exhaustively.

## 3. Operator expectations vs cost for our Tauri/Rust app [I, built on the above]

| Capability | What OpenLP/Companion show | Cost for us | Notes |
|---|---|---|---|
| Slide control over HTTP/WS/OSC | Companion HTTP/OSC verbs; OpenLP `/api/v2/controller/show` + WS | Cheap | Thin bridge over the `AppEvent` bus and existing commands. Add token auth. |
| Companion module (actions/feedbacks/variables/presets) | `IpcTypesNew.ts`, `Presets.ts`, `Variables.ts` | Medium | Separate small TS repo. Needs a stable WS/JSON schema first. |
| Stream Deck hardware | Companion owns it | Free | Document the Companion path. Do not implement HID. |
| Satellite client | `SatelliteApi.ts`, `satellite-protocol/` | Medium, low value | Only for in-app or phone button panels. Conformance corpus exists. |
| MIDI | Not reviewed in either clone | Cheap to medium | `midir` crate; map notes/CC to the same command set. [gap] |
| Service plan (ordered items, save/load, media bundled) | `ServiceItem`, `.osz` zip + `service_data.osj` | Medium | JSON manifest + hashed assets in a zip. Design our own schema. |
| Songs/lyrics with verse order | `Song` model, OpenLyrics XML | Medium | Slide splitting and verse-order logic is the work. The model is small. OpenLyrics is an open spec. |
| Song importers | ~30 importers | Expensive overall; a few cheap | Start with OpenLyrics, ChordPro, CCLI `.usr`/`.txt`, OpenSong (text/XML). |
| Scripture | Per-translation SQLite, 7 importers, reference parser | Medium | Reference parsing and translation licensing are the hard parts. |
| Countdown/service timers | OpenLP has none | Cheap | We already have a slide timer state machine; add a countdown element and variable. A differentiator. |
| Stage display (current/next/notes/clock) | `/stage` from a downloaded bundle | Medium | We already hold notes and next-slide data; a third window or LAN web page fed by the same events. |
| Themes (3-level) | `Theme`, `ThemeLevel` | Medium | Needs a theme schema and a text auto-fit renderer. |
| Alerts/lower-thirds | `AlertsManager` | Cheap | An overlay event plus a presentation-window layer. |
| CCLI usage log + CSV | `SongUsageItem` + CSV | Cheap | Log on slide-live; export CSV. Only meaningful if we do songs. |
| Planning Center import | `PlanningCenterAPI` | Medium | Credentials must follow our keychain rule. |
| PJLink projector control | `pjlink.py` | Cheap to medium | Implement from the public PJLink spec, not from OpenLP code. |
| Native PowerPoint/Keynote drive | COM/UNO/AppleScript | Expensive and fragile | Avoid unless fidelity demands it. |

## 4. Licensing: what is safe to borrow

### Cited findings
- Companion core: MIT (`LICENSE.md` Part 1, `package.json`). Code and protocol definitions may be reused with the notice retained. `satellite-protocol/` is part of the same repo, but its `package.json` licence field was not separately inspected [gap]. The conformance corpus is a good test asset; check the licence field before copying files in.
- Companion module SDK and the generic modules: separate repos, licences not verified here.
- OpenLP: GPL-3.0-or-later (`LICENSE`, headers in every `.py`). Copying or translating its code into our app would force GPL-compatibility. Reading it for ideas is fine.

### Inferences
- **Safe**: the ideas (ServiceItem/capabilities, verse-order slide building, three-level themes, WS state-on-connect, the presentation backend hook list); protocol and format specs (Companion Satellite, PJLink, OpenLyrics, ChordPro, CCLI `.usr` as formats); MIT code from Companion with notice retained.
- **Not safe**: porting OpenLP Python (importers, `serviceitem.py`, theme JSON, render logic, PowerPoint COM hacks) into our code. Implement from format specs and our own test files instead. Do not copy OpenLP's `theme.json` defaults, translations or icons.
- OpenLP's importer mappings are GPL code even where the underlying format is public, so implement from the format documentation.
- This is not legal advice. Do a real licence check before any file-level reuse.
