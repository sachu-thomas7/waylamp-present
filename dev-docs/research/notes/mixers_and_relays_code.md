## voctomix: GStreamer compositor, transitions, layouts, process split

### Takeaway
voctomix builds one `compositor` element and animates pad properties (xpos/ypos/width/height/alpha/zorder) by pre-computing every frame of a transition in Python and loading them as timestamped values into GStreamer control sources, so the GStreamer streaming thread, not Python, applies them frame-accurately. This is directly viable for our F3.3 (fade, side-wipe, fade-to-black at 30 fps), and MIT licensing lets us port the idea or even the pattern directly. Its limits are Python/CPU raw I420 mixing and a fixed single-canvas model.

### Cited Findings
- Mixer is a single `compositor name=videomixer` element. Optional `queue max-size-time=3000000000` (3 s) then `gdkpixbufoverlay name=overlay` (static PNG overlay with alpha), `identity name=sig`, a caps filter, a queue, then `tee name=video-mix`. Each source is `video-<name>. ! videobox name=cropper-<name> ! queue ! videomixer.` and background sources go straight into the compositor. (code-verified) Source: `voctocore/lib/videomix.py` `VideoMix.__init__`.
- Every queue in the whole graph uses `max-size-time=3000000000` (3 s of buffering headroom) rather than tuned small values; that is a stability-over-latency choice. (code-verified) Source: `voctocore/lib/videomix.py`, `voctocore/lib/sources/avsource.py`, `voctocore/lib/sources/tcpavsource.py`.
- Mix format default is raw `video/x-raw,format=I420,width=1920,height=1080,framerate=25/1,pixel-aspect-ratio=1/1`; per-source defaults also 1920 wide and `25/1`. So the compositor runs on CPU raw video, no GPU element. (code-verified) Source: `vocto/config.py` `getVideoCaps` (about line 417-423), source fallbacks lines ~157-191.
- Per-frame animation mechanism: `Scene.__init__` creates, for every property of every source pad, a `GstController.InterpolationControlSource` with `mode = InterpolationMode.NONE` (step mode, no GStreamer-side interpolation) bound via `GstController.DirectControlBinding.new_absolute(pad, prop, cs)`. Properties bound: `xpos, ypos, width, height, alpha, zorder` on the compositor sink pad, and `top/left/bottom/right` on the `videobox` cropper. (code-verified) Source: `voctocore/lib/scene.py` `Scene.__init__` and inner `bind()`.
- `Scene.push(at_time)` writes one control-source value per property per frame at timestamps `time += frame_time` where `frame_time = Gst.SECOND/fps`, starting at the pipeline play time. So an N-frame transition is N timestamped control points, applied by GStreamer in the streaming thread. (code-verified) Source: `voctocore/lib/scene.py` `Scene.push`.
- Scheduling hook: `VideoMix.attach` connects to the `handoff` signal of `identity name=sig`; `on_handoff` checks `scene.dirty` and calls `scene.push(playTime)` where `playTime = pipeline_clock.get_time() - base_time`. Changes requested from the control thread are therefore applied at the next buffer boundary. (code-verified) Source: `voctocore/lib/videomix.py` `attach`, `getPlayTime`, `on_handoff`.
- Cut vs transition: `setCompositeEx` either `scene.set(source, frame)` (single frame = hard cut) or `scene.commit(source, transition.Az(...))` (list of frames = animation); z-order values 100/101 swap during transitions so A/B pass over each other; all non-active sources get `Frame(alpha=0, zorder=-1)`. (code-verified) Source: `voctocore/lib/videomix.py` `setCompositeEx`.
- Transition generation: `Transitions.configure` converts animation ms to frames with `frames = int(fps * time / 1000.0)`; `Transition.calculate` interpolates rectangles along a B-spline (numpy) between key-frame composites; easing is a cosine ease-in/out `smooth(x) = (1 - cos(pi*x))/2`; `morph` interpolates rect size, alpha (int 0-255) and crop. `fade_alpha(frame, alpha, frames)` produces plain cross-fades (used for background fades). Default config ships only `FADE = 750, FULL / FULL`. (code-verified) Source: `vocto/transitions.py` `Transitions.configure`, `smooth`, `morph`, `interpolate`, `fade_alpha`; `voctocore/default-config.ini`.
- Layouts are named composites defined as rectangles in config: fullscreen, picture-in-picture (pip), side-by-side (sbs), side-by-side-preview (sbsp); two sources A and B per composite; `Composite.single()` / `both()` / `covered()` classify them; swapped (`^`) and mirrored (`|`) variants are auto-generated. (code-verified) Source: `vocto/composites.py` (`Composites.configure`, `add_swapped_targets`, `add_mirrored_composites`, `Composite.single/covered`); `doc/transitions.rst`.
- Transition solver rewrites (A,B)->(C,D) requests so a hidden channel B can be secretly swapped, so only A/B pairs ever need animating. (code-verified) Source: `voctocore/lib/videomix.py` `setCompositeEx` three- and four-channel branches.
- Overlay fade uses the same mechanism on a single `gdkpixbufoverlay` alpha property with `InterpolationMode.LINEAR` and two control points (`blend_time` ms apart, default 300 in code). (code-verified) Source: `voctocore/lib/overlay.py` `Overlay.show`.
- Process separation: sources are separate programs (ffmpeg/gstreamer scripts, `example-scripts/`) pushing Matroska over TCP into `tcpserversrc` on ports 10000+ (`Port.SOURCES_IN = 10000`), demuxed with `matroskademux`; core is `voctocore`, UI is a separate program `voctogui` talking a text control protocol over TCP (`Port.CORE_LISTENING = 9999`); mix out on 11000, source previews on 13000+, SRT out via `srtserversink latency=3000`. A NetTimeProvider on the system clock is exposed for distributed time sync. (code-verified) Source: `vocto/port.py`; `voctocore/lib/sources/tcpavsource.py` `build_source`; `voctocore/lib/clock.py`; `voctocore/lib/srtserver.py`; `voctocore/lib/avrawoutput.py` (matroskamux).
- Missing sources are handled by a `videotestsrc` + `textoverlay` ("no signal") feeding a second `compositor-<name>` in front of the real source so the main mixer never starves. (code-verified) Source: `voctocore/lib/sources/avsource.py` (`canvas-{name}`, `nosignal-{name}`, `compositor-{name}`).
- Recording and streaming output use `queue leaky=downstream` before sinks so a slow disk/network cannot stall the mixer. (code-verified) Source: `voctocore/lib/local_recording.py` line ~62/110, `voctocore/lib/srtserver.py` line ~101.
- Prometheus metrics server on port 20000 (per-source info gauges). (code-verified) Source: `voctocore/lib/metrics.py`, `vocto/port.py`.
- Maintenance signs: clone is a single commit, last commit 2026-08-28 touching audio caps; code uses modern typing and `pyproject.toml`/`uv.lock`, plus Dockerfile and Debian packaging. No issue/star data available locally. (code-verified for repo contents only)

### Inferences
- The control-source approach is the key reusable idea for F3.3: precompute per-frame values (rect/alpha/z), push them with timestamps, let the pipeline apply them. In our Rust/GStreamer app the equivalent is `gstreamer-controller` (`InterpolationControlSource` + `DirectControlBinding`) on `compositor`/`glvideomixer` sink pad properties, or simply a Rust-side timer thread at 30 fps setting pad properties. The push-timestamped approach is better than a timer because it is frame-locked and immune to thread jitter. (inferred; mechanism itself is code-verified above, I did not run it)
- A 30 fps fade of 500-750 ms is about 15-23 control points per property; trivial cost. Cut/fade/fade-to-black/side-wipe map to: cut = single `set` frame; fade = alpha ramp on top pad with cosine easing; fade-to-black = alpha ramp to 0 on both plus black background source, or a black source fading in; side-wipe = animate xpos/width of the incoming pad (voctomix's morph does position+size, not a true mask wipe; a wipe revealing via crop would use `videobox`/`crop` properties which voctomix also animates).
- voctomix does NOT use a mask-based wipe; "wipe" in our F3.3 would be a push/slide (rect animation) or a glshader. (inferred from absence in `vocto/transitions.py`)
- The B-spline/numpy corner-path machinery is overkill for four fixed transitions; we only need `smooth()`, lerp over rect/alpha, and the z-order swap trick. (inferred)
- Latency: choices are conservative (3 s queues, 25 fps I420 on CPU), so voctomix is a production tool, not a low-latency one; we should keep queue sizes small (tens to low hundreds of ms) and use leaky downstream queues before encoders/sinks, as voctomix does for recording/SRT. (inferred)
- What limits it: Python on the control path, CPU compositor on raw 1080p25 (no GPU path in this code), at most two visible sources per composite by design (A/B), config-INI defined layouts. (inferred from the code read; no benchmarks were run)
- Licensing: MIT, so we may read, adapt and even copy the `Scene`/control-binding pattern with attribution (keep the copyright notice if substantial code is copied). (inferred legal reading; not legal advice)

### Gaps
- No performance numbers or CPU measurements; none in the repo and nothing was run.
- Did not read `voctogui` or the full control-protocol command list.
- No commit history (shallow clone), so release cadence and bus-factor are unknown.
- Whether `compositor` pad property updates through controllers produce visually tear-free output at 30 fps was not tested; we only know that is the mechanism voctomix relies on.

## CasparCG: mixer/producer/consumer, HTML producer, transitions, AMCP/OSC

### Takeaway
CasparCG is a per-channel frame-clock loop: layers hold producers, the stage composes `draw_frame` trees with transforms, a GPU image mixer renders them to BGRA, and consumers output. Its HTML producer renders CEF off-screen (windowless) into BGRA frames (CPU `OnPaint` memcpy by default, D3D11 shared texture on Windows if GPU enabled) and is driven by an AMCP `CG` command set that calls JS functions `play()/stop()/next()/update(data)/remove()` in the page. The architecture ideas transfer well to our F3.4 overlay engine; the code is GPL-3.0 so only ideas, not code, can be borrowed.

### Cited Findings
- Channel model: each `video_channel` owns `output_`, an `image_mixer_`, a `mixer_` and a `stage_`, and runs a dedicated real-time-priority thread per channel (`set_thread_realtime_priority`, `set_thread_name("channel-N")`) that loops produce (stage) -> mix -> consume per frame. Timing metrics ("produce-time", "mix-time", "consume-time", "frame-time", "osc-time") are exposed via a diagnostics graph. (code-verified) Source: `src/core/video_channel.cpp` `video_channel::impl` constructor and thread lambda.
- Producers/layers/stage live in `src/core/producer/` (`stage.cpp`, `layer.cpp`, `frame_producer.h`, transition producers in `src/core/producer/transition/`); consumers in `src/core/consumer/` (`output.cpp`, `frame_consumer_registry.cpp`); modules provide implementations: `decklink, bluefish, ffmpeg, html, image, newtek (NDI), oal (audio), screen, flash, artnet`. (code-verified) Source: directory listing `src/core`, `src/modules`.
- Mixer: `mixer::impl::operator()` takes a vector of `draw_frame`, for each frame it visits the audio mixer and image mixer (`frame.accept(*image_mixer_)`), calls `image_mixer_->render(format_desc)`, and returns a `const_frame` BGRA image plus mixed audio; it keeps a small future buffer of `field_count` to pipeline GPU readback. (code-verified) Source: `src/core/mixer/mixer.cpp`.
- GPU vs CPU: image mixer has OpenGL (`src/accelerator/ogl/image/image_mixer.cpp`, `image_kernel.cpp`, `shader.frag`) and Vulkan (`src/accelerator/vulkan`) backends chosen in `accelerator::create_image_mixer`; README requires an OpenGL 4.5 GPU. Fragment shader implements keyer, chroma key (hue/softness/spill) and 30 blend modes (`enum class blend_mode`: normal, lighten, ... luminosity, mix). There is no CPU compositing path in the mixer. (code-verified) Source: `src/accelerator/accelerator.cpp`, `src/accelerator/ogl/image/shader.frag`, `src/core/mixer/image/blend_modes.h`, `README.md`.
- Transitions are themselves producers: `transition_producer` takes the old (`leading_producer`) and new (`dst_producer_`) producers and, per frame, `compose()`s two `draw_frame`s with transforms. Types: mix, wipe, slide, push, cut, fadecut, cutfade, vfade (fade through black); directions from_left/right/top/bottom; progress `delta = info_.tweener(current_frame_, 0.0, 1.0, duration - 1)` with tweener name defaulting to "linear"; audio volume is cross-faded with the same delta. Transition does not start until the destination producer `is_ready()`. (code-verified) Source: `src/core/producer/transition/transition_producer.cpp`, `.h` (`caspar::tweener tweener{L"linear"}`), `src/common/tweener.h`.
- Mixer commands operate per layer via frame transforms with tweening: AMCP `MIXER FILL/OPACITY/CROP/ROTATION/PERSPECTIVE/CLIP/KEYER/CHROMA/BLEND/VOLUME/...` plus `MIXER COMMIT` to apply a batch atomically. (code-verified) Source: `src/protocol/amcp/AMCPCommandsImpl.cpp` `register_commands` (list of registered command names); `src/core/frame/frame_transform.h` (tween parameters).
- HTML producer = CEF windowless: `window_info.windowless_rendering_enabled = true`, `browser_settings.windowless_frame_rate = ceil(fps)`, browser sized to the channel's square-pixel width/height; CEF lives on its own executor thread (`g_cef_executor`). (code-verified) Source: `src/modules/html/producer/html_producer.cpp` (`html_producer` ctor ~lines 660-675); `src/modules/html/html.cpp` (`CefInitialize`, `settings.windowless_rendering_enabled = true`).
- How frames arrive: `OnPaint()` (CPU path, default) copies CEF's BGRA buffer with `memcpy` into a `frame_factory_->create_frame(... pixel_format::bgra)` and pushes it on a bounded queue (`frames_max_size_ = 4`, drops oldest with a "dropped-frame" tag); `OnAcceleratedPaint()` (Windows only, only if `configuration.html.enable-gpu` and a D3D device exists) opens the CEF D3D11 shared-texture handle and imports it as a frame (`import_d3d_texture`, BGRA or RGBA). On Linux the code comment says shared texture is not implemented and CPU path measured (March 2026) more performant. (code-verified) Source: `src/modules/html/producer/html_producer.cpp` `html_client::OnPaint` / `OnAcceleratedPaint`; `src/modules/html/html.cpp` `is_gpu_shared_texture_enabled`.
- `receive()` pops a frame if available, else re-serves the last frame as a "still" and flags "late-frame"; there is special handling so interlaced channels do not stutter when CEF only repaints on change (GPU mode). (code-verified) Source: `src/modules/html/producer/html_producer.cpp` `try_pop`, `receive`.
- CEF flags used: `enable-begin-frame-scheduling`, `disable-renderer-backgrounding`, `disable-backgrounding-occluded-windows`, `disable-background-timer-throttling`, `disable-web-security`, `enable-media-stream`; with GPU off also `disable-gpu`, `disable-gpu-compositing`, `disable-gpu-vsync` (comment: otherwise a single 1080p producer cannot run). Remote debugging port and cache path are config-driven. (code-verified) Source: `src/modules/html/html.cpp` `renderer_application::OnBeforeCommandLineProcessing` (~lines 200-252) and `CefInitialize` block (~lines 287-311).
- HTML audio is captured through CEF `OnAudioStreamPacket`, resampled via ffmpeg, and overlaid on the video draw_frame. (code-verified) Source: `src/modules/html/producer/html_producer.cpp` (`GetAudioParameters`, `OnAudioStreamPacket`, `draw_frame::over`).
- Template (graphics) control: AMCP `CG ADD/PLAY/STOP/NEXT/UPDATE/INVOKE/REMOVE/CLEAR`; `html_cg_proxy` translates these to JavaScript calls in the page: `update("<escaped data>")`, `play()`, `stop()`, `next()`, `remove()`, and `invoke(label)` -> arbitrary function call, using `producer_->call({js})`. `CG ADD` does `update(data)` then optional `play()` when play-on-load. Data is passed as a string (typically JSON/XML) with quote/backslash/newline escaping. Templates are loaded from `env::template_folder() + name + ".html"`. (code-verified) Source: `src/modules/html/producer/html_cg_proxy.cpp`; `src/core/producer/cg_proxy.h`; `src/modules/html/producer/html_producer.cpp` (~line 750); registration at `src/modules/html/html.cpp` (`register_cg_producer(... {L".html"} ...)`).
- Protocols: AMCP text protocol (`src/protocol/amcp/*`, with `BATCH`, `LOADBG`, `PLAY`, `CALL`, `INFO`, `DATA STORE/RETRIEVE`, `THUMBNAIL`, `OSC SUBSCRIBE`), and OSC output: `src/protocol/osc/client.cpp` sends channel/layer state (producer name, transition frame/type, audio levels, buffered frames) as OSC bundles via oscpack. (code-verified) Source: `src/protocol/amcp/AMCPCommandsImpl.cpp`; `src/protocol/osc/client.cpp`; `src/core/producer/transition/transition_producer.cpp` `update_state` (`state_["transition/frame"]` etc.).
- Output to streams uses the `ffmpeg` consumer (muxes with libav, arbitrary url/codec options), not a native RTMP/SRT stack. (code-verified for module existence and option parsing) Source: `src/modules/ffmpeg/consumer/ffmpeg_consumer.cpp`.
- Maintenance signs: HEAD commit 2026-10-15 adds a feature (PR #1805); `CHANGELOG.md` top entry "CasparCG 2.5.1 Stable" with fixes; README says it has been in 24/7 broadcast production since 2006; code includes both Vulkan and D3D backends, so active. (code-verified for the listed files)

### Inferences
- Transferable to F3.4: model the overlay as an off-screen Chromium/WebView2 page with transparent background, rendered at channel resolution and fps, with a tiny JS contract (`play/stop/next/update(data)/remove`) invoked from Rust. We already run Tauri (WebView2 on Windows); the closest analogue is an off-screen/hidden webview or CEF OSR. (inferred)
- Alpha: CasparCG's CEF frames are BGRA and the mixer blends them with `opacity` transforms (premultiplied handling lives in shader/blend code I did not fully read). The html producer sets no `background_color` in the code I read, so transparency appears to rely on CEF's default for windowless pages; verify in a spike. (inferred, not verified)
- Frame-delivery lesson: a bounded queue of about 4 frames, drop-oldest, and re-serving the last frame as a still when the browser is late is the robust pattern; page repaint-on-change means a static lower third produces no new frames, so the consumer must hold the last frame. (code-verified mechanism, inference for our use)
- CPU OSR copy of 1920x1080x4 (about 8 MB) at 30 fps is about 250 MB/s memcpy; CasparCG itself says the CPU path is acceptable on Linux and spends extra effort (tbb parallel copy on Windows GPU-enabled path) on it. (arithmetic is mine; the comments are code-verified)
- For a Tauri/WebView2 app, no public API gives frames from a normal webview with alpha at video rate; options are (a) embed CEF OSR (heavy, as CasparCG does), (b) WebView2 `CapturePreview`/composition capture (slow), (c) Windows.Graphics.Capture of an offscreen window (alpha not preserved), (d) draw overlays natively in Rust (e.g. pango/cairo, or GStreamer `textoverlay`/`gdkpixbufoverlay`/`rsvgoverlay`, which voctomix and our compositor can use). This is an open design risk for F3.4. (inferred; not evaluated with code)
- CasparCG's AMCP `MIXER` per-layer opacity/fill/crop with tween and `COMMIT` is a good model for our scene-layer API; our existing AppEvent bus and Tauri commands play the role of AMCP. (inferred)
- Licensing: GPL-3.0. Reading for ideas is fine; copying code into our app would force the combined work under GPL. Running it as a separate process (e.g. as an overlay renderer talking AMCP/OSC) keeps our code independent but you must still honor GPL for CasparCG's own distribution. Not recommended as a dependency anyway: it requires an OpenGL 4.5 GPU and CEF and outputs via its own consumers. (inferred legal reading; not legal advice)

- Did not verify how `stage.cpp` schedules LOADBG/PLAY handoff to the transition producer, nor `tweener.h` easing names.
- No benchmarks; only comments in code about relative performance.
- Whether `CefBrowserSettings::background_color` default yields alpha 0 in windowless mode was not confirmed from this repo.

## MediaMTX: WHIP/WHEP, ingest protocols, API, auth, recording, metrics, hooks; sidecar evaluation

### Takeaway
MediaMTX is a mature, zero-dependency Go media router that does exactly the relay/ingest job (WHIP/WHEP, SRT, RTMP, RTSP, HLS, MoQ in; the same out; native forward to RTMP/RTMPS/SRT/RTSP/WHIP/MoQ destinations; fMP4/MPEG-TS recording; REST Control API; Prometheus metrics; hooks), and it is MIT-licensed so it can be bundled as a sidecar. It remuxes only (no transcoding, no GStreamer), so it can complement but not replace our compositor/encoder path.

### Cited Findings
- Scope statement: "ready-to-use and zero-dependency live media server and media proxy" supporting publish/read over MoQ, SRT, WebRTC, RTSP, RTMP, HLS, MPEG-TS, RTP; recording in fMP4 or MPEG-TS; playback; internal/HTTP/JWT auth; forwarding; proxying; Control API; Prometheus metrics; hooks; hot config reload; single executable on Linux/Windows/macOS. (code-verified) Source: `README.md`.
- Written in Go (`go.mod`: `go 1.27.0`) on `pion/webrtc/v4`, `bluenviron/gortsplib/v5` (RTSP), `gohlslib/v2`, `mediacommon/v2`, `datarhei/gosrt` (SRT). (code-verified) Source: `go.mod`.
- WHIP/WHEP server: HTTP routes `^/(.+?)/(whip|whep)$` (POST creates a session, OPTIONS returns Link header with ICE servers, other methods 405) and `^/(.+?)/(whip|whep)/(.+?)$` (PATCH for trickle ICE, DELETE to end). POST requires `Content-Type: application/sdp`, reads the offer (size-limited), runs auth with credentials from the HTTP request, creates a session, returns `201 Created` with `Content-Type: application/sdp`, `ETag: *`, `ID`, `Accept-Patch: application/trickle-ice-sdpfrag`, `Link` (ICE servers) and `Location` pointing at a secret-bearing session URL, body = SDP answer. CORS preflight headers allow `Authorization, Content-Type, If-Match`. Built-in publish/read web pages are served from `publish_index.html`/`read_index.html`. (code-verified) Source: `internal/servers/webrtc/http_server.go` (`onRequest`, `onWHIPOptions`, `onWHIPPost`, `onWHIPPatch`, `onWHIPDelete`, `sessionLocation`); `internal/servers/webrtc/session.go`; `internal/protocols/whip/link_header.go`, `sdp_fragment.go`.
- Accepted incoming WebRTC codecs registered for publishers include AV1, VP9 (profiles 0-3), VP8, H.265, H.264 with `packetization-mode=1` and `profile-level-id=42001f` or `42e01f` (Baseline/Constrained Baseline), plus RTX variants; audio side includes Opus, G722, PCMU/PCMA, L16. Phone WHIP apps sending Baseline H.264 therefore match. (code-verified) Source: `internal/protocols/webrtc/inbound_track.go` (lines ~24-150); `internal/protocols/webrtc/from_stream.go` (outbound codecs).
- Other ingest: SRT server (`internal/servers/srt`, uses `streamid`, auth protocol SRT in `conn.go`), RTMP/RTMPS server, RTSP/RTSPS server, HLS, MoQ servers under `internal/servers/*`; static pull sources (`internal/staticsources/{hls,moq,mpegts,rpicamera,rtmp,rtp,rtsp,srt,webrtc}`) to pull from remote endpoints. (code-verified) Source: directory listings of `internal/servers`, `internal/staticsources`.
- Forwarding (multi-destination egress): per-path `forward:` list in config; each entry `dest` supports `rtsp(s)://`, `rtmp(s)://host/path#streamKey`, `srt://host:port?streamid=`, `moqt://`, `whip(s)://` (with `whipBearerToken`); `$MTX_PATH`/`$G1` substitution; `retryPause = 5 * time.Second` on failure; per-destination `ForwardDestInfo{OutboundBytes, TypeSpecific}` readable through the API and exported as metrics `forward_dests_outbound_bytes`. Docs include YouTube and Twitch examples. (code-verified) Source: `internal/forward/manager.go` (`resolveDest`, `destType`, `retryPause`), `internal/forward/{rtmp,srt,rtsp,webrtc,moq}/`, `internal/defs/forward_dest_info.go`, `mediamtx.yml` (forward section lines ~544-570), `docs/2-features/10-forward.md`, `internal/api/api.go`.
- Control API (REST, gin): `GET /v3/info`; config CRUD for global, path-defaults, paths (`/config/paths/add|patch|replace|delete/*name`) and internal users; `GET /paths/list|get/*name`, `/paths/forward-dests/list|get`, `/paths/static-sources/get/*name`; list/get/kick for hls muxers+sessions, rtsp/rtsps/rtmp/rtmps conns+sessions, webrtc sessions, srt conns; recordings endpoints (`api_recordings.go`). Paths can be added/removed at runtime without restart. ### Inferences
- As F4 egress sidecar: pipe our encoded program stream (e.g. SRT or RTMP or RTSP loopback publish from GStreamer) into one MediaMTX path and configure `forward:` to YouTube/Twitch/Facebook/custom RTMP(S)/SRT targets. This gives multi-destination fan-out, per-destination retry (5 s), per-destination byte counters and an API/metrics for health, without re-encoding per destination. Adding/removing destinations at runtime is possible through `/v3/config/paths/patch/*name` (from the config-paths API). (inferred from verified features; not tested)
- Caveat: forward is remux-only; per-destination bitrate/resolution variants need separate encodes in our GStreamer pipeline. Destination health beyond OutboundBytes is thin (no per-destination state/error reason in `ForwardDestInfo` as read; errors go to logs). (inferred from the struct and the retry loop)
- As F2.4 phone ingest: MediaMTX gives a production-grade WHIP server (trickle ICE PATCH, TURN/ICE-server Link header, auth, CORS, built-in browser publish page) which would save our axum/whipserversrc work. But it would then be the receiver, so we would consume its output (RTSP/SRT/RTMP loopback or WHEP) into GStreamer for preview/compositing, adding a hop and codec payload re-parsing, and an extra process to package and supervise. We already have a working GStreamer `whipserversrc` path verified over loopback; keep ours for the in-process tight loop unless NAT/TURN robustness proves a problem. (inferred; trade-off, not tested)
- Borrowable design points for our own axum WHIP (all MIT, code-verified patterns): the 201 response header set (`Location`, `ETag`, `Link`, `Accept-Patch`), the secret-in-Location session URL, OPTIONS returning ICE servers in `Link`, 405 on unexpected methods, size-limited SDP body, `Content-Type` check, auth-before-session. Our F2.4 already implements 409/503/401 and PATCH/DELETE/OPTIONS; compare Link/ETag/ID headers and `application/trickle-ice-sdpfrag` handling against `internal/servers/webrtc/http_server.go`. (inferred; comparison against our code not performed)
- SRT stats list (`srt_conns_*`) is a ready checklist for F4 stream-health fields (loss, retrans, RTT, send buffer, bitrate); our streaming health UI could mirror these names. (inferred)
- Complexity: Go single binary, but about 15 internal packages and large pion/gortsplib dependency tree; for use as a sidecar the integration cost is low (config file + HTTP API), for code reuse it is not applicable (different language). (inferred)
- Licensing: MIT, so we can ship the binary as a sidecar (include its license text and notices of its dependencies) and may copy small code fragments with attribution; unlike GPL, no copyleft on our app. (inferred legal reading; check bundled dependency licenses before shipping; not legal advice)
- Bundling concerns: extra executable per OS (Windows AV false positives already a noted issue in our CLAUDE.md for unsigned binaries), port conflicts (default listeners for RTSP/RTMP/HLS/WebRTC/SRT/API/metrics must be disabled or rebound to localhost), and needing to supervise the process lifecycle from Tauri. ## Concrete takeaways for our roadmap (F2.4, F3.1-F3.4, F4)

### Takeaway
Use voctomix's pattern for F3.3 transitions (pre-computed, timestamped pad-property control sources), CasparCG's producer/draw-frame/transform/tween and `play/stop/next/update(data)` template contract as the model for F3.4, and treat MediaMTX as an optional, MIT-licensed egress/relay sidecar for F4 rather than a replacement for our WHIP ingest in F2.4.

### Cited Findings
- (F3.1/F3.2) Single `compositor` with per-source `queue`s and per-source pads, A/B z-order swap and "invisible = alpha 0, zorder -1" instead of unlinking pads; allows source add/remove without relinking mid-transition. voctomix: `voctocore/lib/videomix.py`, `voctocore/lib/scene.py`. (code-verified)
- (F3.1) "No signal" fallback: put a test-pattern/text source behind each real source in a small per-source compositor so the main mixer never starves. voctomix: `voctocore/lib/sources/avsource.py`. (code-verified)
- (F3.3) Transition engine essentials: `frames = int(fps*ms/1000)`; ease `smooth(x) = (1-cos(pi x))/2`; per-frame lerp of rect/alpha/crop; apply by control source timestamps = `playTime + i*(1s/fps)`; commit from control thread, apply on a pipeline buffer handoff. voctomix: `vocto/transitions.py`, `voctocore/lib/scene.py`, `voctocore/lib/videomix.py`. (code-verified)
- (F3.3) CasparCG's set of transition names (cut, mix, wipe, slide, push, fadecut, cutfade, vfade) and its `vfade` special handling (a single black frame at the midpoint) are a ready taxonomy and edge-case list for even/odd durations. CasparCG: `src/core/producer/transition/transition_producer.cpp`. (code-verified)
- (F3.4) HTML overlay: CEF OSR to BGRA with bounded drop-oldest frame queue, hold-last-frame when no new paint, JS contract `play/stop/next/update/remove/invoke`. CasparCG: `src/modules/html/producer/html_producer.cpp`, `html_cg_proxy.cpp`. (code-verified)
- (F3.4 alt) voctomix's overlay is only a PNG `gdkpixbufoverlay` with alpha fade via a LINEAR control source; this is the cheap fallback for static lower-thirds. `voctocore/lib/overlay.py`. (code-verified)
- (F4) MediaMTX `forward:` entries for rtmp(s)/srt/rtsp/whip/moqt with retry and byte counters, plus `srt_conns_*` stats, are a ready egress and health design. `internal/forward/manager.go`, `internal/metrics/metrics.go`. (code-verified)
- (F4/F2.4) voctomix uses `leaky=downstream` queues before recording/SRT sinks and SRT `latency=3000` as a stability default; MediaMTX records fMP4 with 1 s parts and 1 h segments by default. `voctocore/lib/srtserver.py`, `mediamtx.yml`. (code-verified)

### Inferences
- F3.3 viability at 30 fps: yes. voctomix proves the mechanism at 25 fps 1080p I420 on CPU with Python control; ours should be at least as good with Rust control and, if we use `glvideomixer`, a GPU path. Risk: confirm `GstController` bindings work on our chosen mixer element's pad properties (they do for `compositor` per voctomix; not verified for `glvideomixer`). (inferred)
- Make fade-to-black a dedicated transition (alpha on both to black background) rather than a cross-fade, as CasparCG distinguishes `vfade`. (inferred)
- Sidewipe: implement as slide/push (animate xpos/width), same as CasparCG push/slide and voctomix morph; true mask wipes need a shader. (inferred)
- Do not copy CasparCG code (GPL-3.0); voctomix and MediaMTX (MIT) are safe to adapt with notices. (inferred legal reading)
- F4: start with GStreamer-native `rtmp2sink`/`srtsink` per destination if there are 1-3 destinations, as it keeps one binary; adopt a MediaMTX sidecar if we need many destinations, runtime reconfiguration through an HTTP API, or built-in recording/health metrics. This is a product decision; the code gives feasibility, not a recommendation of one winner. (inferred)
