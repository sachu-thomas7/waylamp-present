## 1. Data model: shows, slides, layouts, groups, projects, templates, overlays, scenes; storage, undo, backup, cloud

### Takeaway
Shows are one JSON file each (`.show` = `[id, Show]`) in `Documents/FreeShow/Shows`; everything else lives in a few electron-store JSON files fed by a single renderer-side Svelte-store "world" that is pushed whole to main on save. Undo is an in-renderer history stack persisted to history.json; backup is zip; cloud sync is a per-item merge ledger against ChurchApps (a Google Drive path also exists).

### Cited Findings
- Show schema: `Show{name, category, settings{activeLayout, template, customFonts}, timestamps, meta{title,artist,author,CCLI,...}, slides:{id:Slide}, layouts:{id:Layout}, media:{id:Media}, midi?}`; `Slide{group, color, settings, children[], notes, items[], timeline?}`; `Layout{name, notes, timeline?, slides: SlideData[]}`; `SlideData` carries per-layout-slot state (disabled, parent, children, nextTimer, transition, background, overlays, effects, audio, mics, `actions{slideActions, receiveMidi, nextAfterMedia, startShow, clear*}`, `bindings` to an output). Slides/groups are shared and layouts are ordered references with per-reference overrides (song-arrangement model). — [src/types/Show.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/types/Show.ts)
- Slide content is a list of typed `Item`s: text, media, camera, timer, clock, button, events, weather, variable, web, qr_code, icon, slide_tracker, visualizer, captions, metronome, current_output, chart, table. Items carry a CSS-string `style`, per-item `conditions`, `actions.transition` (show/hide timers), `bindings`, chords, scrolling, click/line reveal. — same file (`interface Item`, `type ItemType`)
- Overlays, Templates and Scenes are separate stores: `Overlay{items, displayDuration, placeUnderSlide, actions}`; `Template{settings{mode default|scripture|item|text, resolution, maxLinesPerSlide, breakLongLines, styleOverrides regex}, items}`; `Scene{name, bindings, action, content{media, style, overlays, hiddenOverlays}}`. — same file
- On-disk layout: electron-store files from `storeFilesData`: SHOWS (trimmed minified index cache), SETTINGS, SYNCED_SETTINGS, THEMES, PROJECTS ({projects, folders, projectTemplates}), STAGE, OVERLAYS, TEMPLATES, EVENTS (portable ones go to `<DataRoot>/Config`), HISTORY, MEDIA, CACHE, USAGE, ERROR_LOG, ACCESS (contentProviders and `secrets` in a plain JSON store, no OS keychain). Folders (`dataFolderNames`): Shows, Backups, Bibles, Online, Media, Exports, Imports, Lessons, Planning Center, Recordings, Audio, Config, Cloud; default root `Documents/FreeShow`. — [E/data/store.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/data/store.ts), [E/utils/files.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/utils/files.ts)
- Save path: the renderer builds one whole `SaveData` object and calls main `save(data)`; main writes each changed store, each show to `Shows/<name>.show` as `JSON.stringify([id, value])`, bibles to `Bibles/<name>.fsb`. It early-returns if `isSaving` is already true (a concurrent save request is dropped). `checkStores` deletes any store JSON that fails `JSON.parse` at startup and deletes history.json if over 30 MB. — [E/data/save.ts `save()`](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/data/save.ts), store.ts `checkStores`
- Undo/redo: `history(obj)` in the renderer with a legacy per-id `switch` (textStyle, deleteItem, setItems, ...) plus a newer `HistoryNew{version,time,type store_create|store_update|store_delete,value}`; `undo`/`redo` stacks persisted to history.json; consecutive edits merge via `location.override`; no-op changes skipped via `isNoDataChange`; `historyActions.ts` is 966 lines. — [T/History.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/types/History.ts), [F/components/helpers/history.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/components/helpers/history.ts)
- Backup: `startBackup` zips portable store files and shows (plus bibles for cloud) into `Backups/<timepoint>[_auto].zip`; auto backups skip shows and are pruned (`pruneAutoBackups`). — [E/data/backup.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/data/backup.ts)
- Cloud sync: `syncManager.ts` (760 lines) + `syncLedger.ts` merge per item for `MERGE_INDIVIDUAL = [OVERLAYS, PROJECTS, STAGE, TEMPLATES, SYNCED_SETTINGS]`; only provider id `churchApps` (`ChurchAppsSyncManager.ts`); a Google Drive implementation `cloud/drive.ts` (563 lines) also exists. The biggest test file in the repo is `syncManager.test.ts` (1,475 lines). — [E/cloud/syncManager.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/cloud/syncManager.ts)
- Content providers: Planning Center (incl. PCO Live timer sync), ChurchApps, Canva, Amazing Life, OnStage under `src/electron/contentProviders/` (directory listing).

### Inferences
- The Show/Layout/SlideData split is a good reference model for our deck model (arrangement reuse, per-slot overrides for transition/background/overlays/actions).
- Whole-state save from a renderer plus "drop concurrent save" is a data-loss risk under rapid edits or a renderer crash (inferred, not reproduced).
- Provider secrets in a JSON store vs our keychain-only rule is a security advantage for us.

### Gaps
- Schemas for the `styles`, `outputs`, `timers`, `variables` stores were not read in detail.
- Behaviour of the `isSaving` early return under load was not tested.

## 2. Output architecture: windows, offscreen rendering, per-output settings, state sync, multi-screen/hotplug, stage display, capture fan-out and costs

### Takeaway
Each output is a full Chromium BrowserWindow running the same Svelte app (`MainOutput.svelte`), driven by IPC state snapshots. Capture-only ("invisible") outputs use Electron offscreen rendering with a shared-texture path and a native readback addon (osr-capture); visible outputs are captured by polling `capturePage()`. Every egress (NDI, OMT, Blackmagic, WHIP, RTMP, recorder, web preview) is fed raw BGRA frames read back from GPU to CPU, with a large amount of adaptive throttling to contain the cost.

### Cited Findings
- Per-output config: bounds, boundsLocked, cropping, edge `blending{left,right,rotate,opacity,centered,offset}`, screen id, alwaysOnTop, `transparent` (alpha/key), ndi/ndiData, omt/omtData, blackmagic/blackmagicData, webrtc/webrtcData{url,token,fps,bitrate}, rtmp/rtmpData{destinations[],encoder,rateControl,fps,bitrate}, forcedResolution, `invisible`, `stageOutput` (an output can show a stage layout), and `out{background, slide, effects, overlays, transition, scene}`. — [T/Output.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/types/Output.ts)
- Windows: `OutputLifecycle.createOutput` creates a `new BrowserWindow` per output (frameless, skipTaskbar, alwaysOnTop default true, `type:"panel"` in some cases) and loads the same bundle via `loadWindowContent(window,"output")`; the window renders `Output.svelte`, or `StageLayout.svelte` when `stageOutput` is set. Capture starts via a 1,200 ms timer after creation. — [E/output/helpers/OutputLifecycle.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/output/helpers/OutputLifecycle.ts), [F/MainOutput.svelte](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/MainOutput.svelte)
- State sync: the controller window is the single source of truth. Store subscribers (`storeSubscriber` in `listeners.ts`, debounced by `hasNewerUpdate`) call `send(OUTPUT, ["OUTPUTS"], data)`; main's `OutputHelper.receiveOutput` -> `OutputSend.sendToOutputWindow` clones the message and `webContents.send`s it to each output window (per-output filtering for "OUTPUTS"). The full `showsCache` is pushed with `send(OUTPUT, ["SHOWS"], data)` on every change. — [E/output/helpers/OutputSend.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/output/helpers/OutputSend.ts), [F/utils/listeners.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/utils/listeners.ts)
- Multi-screen/hotplug: `OutputLifecycle.initListeners` hooks Electron `screen` events `display-metrics-changed` (500 ms delay), `display-added` (1,000 ms), `display-removed` and runs `restoreAllOutputBounds`. `OutputVisibility.resolveOutputBounds` order: saved bounds if their centre lies on a live display; else the saved `screen` id (unless it is mostly covered by the main window, `amountCovered > 0.5`); else, if autoPosition and not macOS, the "second display" not covered by the main window. `updateBounds` calls `setBounds` three times (0/10/80 ms; comment "has to be set twice to work first time"). — [OutputVisibility.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/output/helpers/OutputVisibility.ts), [OutputBounds.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/output/helpers/OutputBounds.ts)
- HiDPI: capture-only outputs render at `bounds / scaleFactor` so `capturePage()` device pixels equal the configured resolution (`getRenderBounds`); on Linux a 1 px size bump avoids an X11 shrink bug when window equals screen size (`avoidLinuxDisplaySizeShrink`). — OutputBounds.ts, OutputLifecycle.ts
- Offscreen (OSR) applies only to `invisible` outputs (`isInvisible`): `webPreferences.offscreen = {useSharedTexture:true}` when the native `osr-capture` addon loads AND GPU compositing is hardware (`useSharedTextureCapture`), else CPU-bitmap offscreen. Render rate is 60 fps while a receiver is connected, 1 fps when idle (`CaptureHelper.updateRenderRate`); Linux needs a timer calling `webContents.invalidate()` to force begin-frames. Comment in `updateFramerate`: rendering several 4K OSR surfaces at 60 fps saturates the GPU and balloons every readback from ~20 ms to ~100 ms. — OutputLifecycle.ts (`attachOsrCapture`, `updateOsrPaintDrive`), [E/capture/CaptureHelper.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/capture/CaptureHelper.ts)
- "GPU-native capture" in practice: the `paint` event hands a shared texture handle to a worker thread, which calls the addon (`readbackConsume`, `convertBgraToUyvy`, `downscaleBgra`; formats 0=BGRA, 1=UYVY, 2=UYVA, 3=RGBA) for GPU->CPU readback, colour conversion and (for web previews) GPU downscale. It is still a GPU->CPU readback, not zero-copy into an encoder. Mitigations: adaptive pipeline depth `ceil(targetFps*minRtt)+1` with 2-evaluation hysteresis, global pool cap 16 (`ADDON_MAX_POOL`), coalescing rapid paints into one pending frame, admission timers, early texture release, a park watchdog, and `FS_CAP_STATS=1` per-second hop telemetry. — OutputLifecycle.ts (`attachOsrSharedTexture`, `deriveDepthFor`, `tryAdmit`), [E/capture/SenderCapture.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/capture/SenderCapture.ts), [E/capture/senderWorker.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/capture/senderWorker.ts)
- Non-OSR (normal visible window): `CaptureLifecycle.runCaptureLoop` polls `webContents.capturePage()` in a `setTimeout` loop at the max configured channel rate; idle backoff to 3 fps after 2 s of unchanged content (not for NDI/Blackmagic); Blackmagic is throttled by `process.memoryUsage().external` (over 3/4/5/6 GB -> 10/8/6/4 fps). Change detection: FNV hash over a 64x36 jittered pixel grid, with a 1 s keepalive for unchanged frames. Heavy consumers (server/stage JPEG) are capped at 12 fps above 4 MP and 20 fps above 2 MP. — [CaptureLifecycle.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/capture/helpers/CaptureLifecycle.ts), [CaptureTransmitter.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/capture/helpers/CaptureTransmitter.ts)
- Default per-channel rates (`CaptureHelper.framerates`): stage 20, web output-stream 10, WebRTC 30, RTMP 30, recorder 30, NDI/OMT 30 when connected else 1. Channels: ndi, omt, blackmagic, server, stage, webrtc, rtmp, recorder. — CaptureHelper.ts
- NDI/OMT send: one `worker_threads` worker per protocol sharing `senderWorker.ts` (pacer, BGRA->UYVY/UYVA conversion, timecode stamping, connection polled every 250 ms) with adapters `ndiWorker.ts` (npm `grandiose`, ChurchApps fork) and `omtWorker.ts` (`openmediatransport`). Alpha is supported through UYVA when the output is `transparent`. — [E/ndi/ndiWorker.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/ndi/ndiWorker.ts), package.json
- NDI/OMT/Blackmagic receive: runs in an Electron `utilityProcess` (`StreamReceiverHost.ts`, `streamReceiverProcess.ts`); each renderer gets a `MessageChannelMain` port so frames flow child->renderer without passing through main; the renderer converts UYVY on the GPU with a WebGL fragment shader (`streamCanvas.ts`, BT.601 vs 709 switch at 720 lines) with a CPU fallback; the controller gets a nearest-neighbour 480 px preview. — [E/capture/StreamReceiverHost.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/capture/StreamReceiverHost.ts), [E/capture/streamFrames.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/capture/streamFrames.ts)
- Blackmagic: SDI/HDMI out through npm `macadam` (DeckLink): 8/10/12-bit converters, audio queue, a global init mutex (comment: simultaneous inits on different ports of the same card can crash the DeckLink SDK native layer), and a `SEGFAULT_PRONE_DEVICES` set. — [E/blackmagic/BlackmagicSender.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/blackmagic/BlackmagicSender.ts)
- RTMP egress is out-of-process: `RtmpStreamer.ts` spawns an `ffmpeg` child (looked up on PATH, system paths, or `userData/bin`; `ffmpegManager.ts` pins `FFMPEG_VERSION b6.1.1` for runtime download) with raw BGRA on `pipe:0`, PCM on `pipe:3`, FLV on stdout, then one `-c copy` relay ffmpeg per destination (multi-destination). Reconnect backoff 1 -> 15 s (forgiven after 60 s alive); hardware encoder detection and fallback (x264, nvenc, qsv, amf, videotoolbox, vaapi profiles in `encoderProfiles.ts`). — [E/streaming/RtmpStreamer.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/streaming/RtmpStreamer.ts), [encoderProfiles.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/streaming/encoderProfiles.ts), [ffmpegManager.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/streaming/ffmpegManager.ts)
- WHIP/WebRTC egress: `WebRtcHost.ts` creates a hidden BrowserWindow (nodeIntegration on, contextIsolation off) containing a `canvas`, `captureStream(fps)` and `RTCPeerConnection`; main pushes RGBA frames into the canvas; WHIP POST/DELETE are done from main via Node `fetch` (User-Agent "OBS/30.0.0") to avoid CORS. Path: GPU readback -> CPU -> IPC -> canvas -> Chromium encoder. — [E/streaming/WebRtcHost.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/streaming/WebRtcHost.ts)
- Recorder: renderer-side `MediaRecorder` (WebM VP9/Opus, 1 s chunks) in `drawer/live/recorder.ts`, fed from the same capture frames; no ffmpeg/MP4 recording path found. An Icecast audio sender exists (`E/audio/IcecastSender.ts`). — [F/components/drawer/live/recorder.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/components/drawer/live/recorder.ts)
- Stage display: `StageLayout{items, settings, password}`; item type `current_output` mirrors an output live. Stage web clients (port 5511) only receive JPEG frames when subscribed (`STREAM_SUBSCRIBE` with 10 s TTL heartbeat), capped 10 fps / 1,280 px; capture for "stage" is enabled only while a connected client views such an item (`shouldBeCaptured`). — [T/Stage.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/types/Stage.ts), [E/servers.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/servers.ts), [F/components/helpers/output.ts `shouldBeCaptured`](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/components/helpers/output.ts)
- GPU selection: Linux pins a DRM render node (`--render-node-override`), macOS forces high-performance or low-power GPU, Windows has no selector; Linux enables VA-API decode via command-line features. — [E/utils/gpu.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/utils/gpu.ts), [commandLineSwitches.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/utils/commandLineSwitches.ts)
- A "shared-render follower" concept (outputs sharing another output's window) is referenced in `OutputSend.ts`, `StreamReceiverHost.ts` and `OutputLifecycle.ts` via `(output as any).follower`, but no code that creates followers was found in the clone; looks partially landed. — those three files

### Inferences
- "GPU-native capture" here means GPU compositing + native async readback + native colour convert/downscale off the main thread. It avoids Electron's slow `capturePage` and main-thread stalls, but is still bandwidth-bound (their own comments: several 4K outputs at 60 fps saturate the GPU). Our GStreamer compositor can keep frames on GPU into NVENC/QSV/VAAPI and read back once only for NDI; a real structural advantage.
- Visible projector windows (the common church case) use the slower polling `capturePage` path when NDI/streaming is also on; only `invisible` outputs get the optimised path (inferred from `osr: this.isInvisible(output)`).
- The volume of adaptive-throttle code (depth estimator, pools, parking, memory-based backpressure) signals the Electron readback architecture is fragile at 4K/multi-output.
- Pushing the whole `showsCache` to every output window over IPC will scale poorly with large decks (inferred from `send(OUTPUT, ["SHOWS"], data)`).

### Gaps
- osr-capture, grandiose, macadam, openmediatransport native code (the actual GPU path) is external and unread. The repo gives no measured fps/latency beyond code comments (~20 ms single readback, ~100 ms contended).
- Whether "follower" shared rendering is used anywhere in the UI was not established.
- No CPU/GPU benchmark figures exist in the repo; none claimed.

## 3. Transitions, scenes, camera items and their limits

### Takeaway
Transitions are Svelte transitions on DOM layers (fade, blur, scale, fly, 4-direction slide, spin; no shader wipes, no true two-source crossfade). "Scenes" are NOT a multi-source compositor: a Scene is a saved bundle of one media source (camera/screen/NDI/OMT/Blackmagic), a style and some overlays, shown on bound outputs. Cameras are `getUserMedia` `<video>` elements.

### Cited Findings
- Transition engine: `utils/transitions.ts` offers `none, blur, fade, crossfade (commented out of the UI list), fly, scale, slide, spin` with easings linear/back/sine/circ/cubic/elastic/bounce, applied by Svelte `in:`/`out:` directives in `OutputTransition.svelte`; `SlideItemTransition.svelte` keeps outgoing and incoming items in the DOM; priority item > slide > style > global; item show/hide delay timers. Comments flag WIP issues ("item wait out time will not clear other items...", "slide direction from top to bottom is a bit buggy", "image is flashing a bit in scripture transition none") and a "svelte transition bug!!!" workaround. — [F/utils/transitions.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/utils/transitions.ts), [OutputTransition.svelte](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/components/output/transitions/OutputTransition.svelte), [SlideItemTransition.svelte](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/components/output/transitions/SlideItemTransition.svelte)
- Transition model: `Transition{type,duration,easing,fadeInOffset,delay,custom,between,in,out}`; separate `mediaTransition` on `SlideData`. — Show.ts
- Scene activation: `startScene(id)` resolves target outputs from `scene.bindings`, skips if already active, calls `setOutput("scene", {...content, id, name})` per output, then runs `scene.action`; `updateActiveSceneOutputs` re-pushes live edits. The scene editor (`SceneTools.svelte` 251 lines, `SceneEditor.svelte` 78 lines) edits overlays and style. — [F/components/helpers/output.ts `startScene`](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/components/helpers/output.ts), [F/components/edit/SceneTools.svelte](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/components/edit/SceneTools.svelte)
- Scene media layer: `SceneMedia.svelte` renders exactly one source of type camera | screen (`Window.svelte`) | ndi | omt | blackmagic, full-frame (`object-fit: cover` for camera). — [SceneMedia.svelte](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/components/output/layers/SceneMedia.svelte)
- Cameras: `Camera.svelte` attaches an `HTMLVideoElement` via `cameraManager.attachCamera` (browser `getUserMedia`), applying crop/flip/filter in CSS; slides can hold `camera` items; a phone camera web app exists in `src/server/cam/` (the `CAM` server port is commented out in `serverPorts`). — [Camera.svelte](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/components/output/Camera.svelte), servers.ts
- Effects: a 3,009-line Canvas2D particle/effects renderer (`effectRenderer.ts`, ~26 types incl. rain, snow, aurora, fireworks, mesh_gradient, rays); uses `getContext("2d")`, not WebGL. — [effectRenderer.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/components/output/effects/effectRenderer.ts)
- Timeline: slide/show timelines of timed actions (`TimelineAction{time,duration,type action|slide|show|audio|style, easing}`) plus LTC and MTC timecode input (`E/timecode/`). — Show.ts, `F/components/timeline/*`

### Inferences
- No picture-in-picture, multi-source layout, per-source geometry or keying in "Scenes". Our F3.1 compositor (scene geometry, runtime add/remove) already exceeds this on the production side.
- DOM/CSS transitions cannot give frame-accurate crossfades between two live video sources; a GPU compositor can.

### Gaps
- `cameraManager` enumeration/hot-plug logic not read.
- `crossfade` is in the `TransitionType` union but absent from the UI list; its real behaviour was not verified.

## 4. Importers: PPTX/PDF/Keynote/ProPresenter/EasyWorship/OpenLP and others

### Takeaway
PPTX import is a genuine structural parser (OPC package, master/layout/slide inheritance, shapes, gradients, embedded fonts/media) producing editable Items, not rasters; gaps are admitted in comments. PDF is rendered per page via pdf.js. Keynote has no importer, only live control via AppleScript. Song-format importers are many and small.

### Cited Findings

## 5. Control surface: Companion/WebSocket/REST/OSC/MIDI, actions model, web remote/stage apps, auth

### Takeaway
Every control path funnels into one `API_ACTIONS` table (~150 actions, with `get_*` queries returning data) executed in the controller Svelte renderer. Transports: WebSocket (socket.io) on 5505, REST on 5506 (`port+1`), OSC over UDP on 5505, MIDI via JZZ, plus four built-in web apps. Auth is one optional shared password over plain HTTP.

### Cited Findings
- API server: `DEFAULT_PORTS = {WebSocket: 5505, REST: 5506}`; `startWebSocketAndRest({port,password})` starts REST on `port+1`, socket.io on `port` (CORS `*`), and OSC (`osc-js` UDP, host 0.0.0.0, same port as the WebSocket; address `/freeshow/<action>`). Message shape `{action, ...data}`; REST accepts any method on `/` with a JSON body or `?action=ID&data={json}`; `get_*` actions get a `returnId` and the call waits up to 10 s for the renderer's reply (204 if none). — [E/utils/api.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/electron/utils/api.ts)
- Auth: one optional password (`apiPassword`); accepted from `Authorization: Bearer`, headers (`x-api-key` etc.), query string (`password`, `token`, `key`...), body, socket handshake auth/query, or OSC args; empty password means no auth; plain `===` comparison; no TLS, no per-action scopes, no rate limiting found; REST uses `app.listen(PORT)` (all interfaces). — api.ts (`getAuthToken`, `checkAuth`)
- Execution happens in the renderer: `receivedData` does `sendToMain(ToMain.API_TRIGGER2, data)` to the main window; `API_ACTIONS` in `F/components/actions/api.ts` maps ids to functions, many tagged `// BC` meaning integrated into Bitfocus Companion. A hung or closed controller renderer means nothing executes. — api.ts, [F/components/actions/api.ts](https://github.com/ChurchApps/FreeShow/blob/436d4b634878ba723da1d1373637384ec700ce16/src/frontend/components/actions/api.ts)
- Action inventory (keys of `API_ACTIONS`): projects (id/index/name select, next/prev item, mark played), shows (select, start, change_layout, set_plain_text, set_show, rearrange_groups, add_group, set_template, next-slide-timer, transpose), presentation (next/previous/random slide, index/name select, id_select_group, disable_slide), clear (restore_output, clear_all/background/slide/overlays/overlay/audio/next_timer/scene/drawing), media (start_camera, start_screen, play_media, toggle playing/loop/mute, video_seekto), overlays/effects, scripture (start, next, previous), `start_scene`, streaming (`start/stop_webrtc_stream`, `start/stop_rtmp_stream`, `start/stop_output_recording`), outputs (lock_output, toggle_output_windows, toggle_output, id_select_output_style, change_output_style, change_stage_output_layout, change_transition, id_select_stage_layout), audio (play/pause/stop, seekto, volume, mute, audio stream, record, icecast, playlists, metronome, effects, microphone), timers (start/pause/stop by id or name, seek, edit), timeline, `change_variable`, draw zoom, `sync_content_provider`, `send_midi`, `send_rest_command`, `emit_action`, interactions, OBS (`obs_set_scene`, `obs_start/stop_livestream`, `obs_start/stop_recording`), Spotify, STT toggle, project CRUD, `run_action`/`name_run_action`/`toggle_action`. Queries: get_shows, get_show, get_show_layout, get_projects, get_project, get_plain_text, get_groups, get_output, get_output_slide_text, get_output_group_name, get_dynamic_value, get_playing_video_* and get_playing_audio_* (duration/state/time/time_left/data), get_variables, get_variable, get_timers, get_actions, get_playlists, get_playlist, get_slide, get_thumbnail, get_slide_thumbnail, get_pdf_thumbnails, get_cleared. — api.ts (frontend)

### Inferences
- The `// BC` markers imply a Bitfocus Companion module (not in this repo; unverified) built on this contract. Matching the `{action, ...}` shape and `get_*` ids would give cheap Companion compatibility.

### Gaps
- Not diffed against the Companion module (unavailable here).
- Remote/stage web-app auth beyond the password checks was not exhaustively reviewed.

## 9. Gaps and opportunities vs our planned design

### Takeaway
Our largest structural wins: GPU/GStreamer-native compositing and encode without a CPU readback per consumer; a Rust-owned deterministic state machine independent of any UI renderer; PPTX fidelity beyond FreeShow's admitted gaps; a hardened control API. FreeShow's lead is feature breadth (songs, scripture, audio, remotes, imports, cloud sync, AI).

### Cited Findings (tied to code already cited above)
- Egress cost: each consumer takes raw BGRA via GPU->CPU readback (`CaptureTransmitter.sendRaw*`, `senderWorker.ts`); RTMP pipes raw frames into external ffmpeg (`encoderProfiles.ts`: `-f rawvideo ... pipe:0`); WHIP re-injects frames into a hidden canvas (`WebRtcHost.ts`). — section 2 files
- Compositing: Scenes hold one media source (`SceneMedia.svelte`, `SceneContent`), no layout geometry/PiP/keying. — section 3
- Control logic runs in the renderer; API open by default over HTTP, password accepted in query. — section 5
- Visible projector outputs use polling `capturePage` rather than the OSR path. — OutputLifecycle.ts, CaptureLifecycle.ts

### Inferences (opportunities and risks for us)
- Beat them: appsrc/GL compositor -> hardware H.264 (`nvh264enc`/`qsvh264enc`/`vah264enc`) -> RTMP/SRT/WHIP in-process, NDI from a single GPU download; per-source geometry compositing, runtime add/remove, alpha/key fill output; avoids the memory-bandwidth wall FreeShow documents with multiple 4K outputs.
- Beat them: capability-minimal windows (presentation listen-only), keychain secrets, token-scoped and TLS-capable remote API with typed schema, a testable Rust state machine, invariants tests and E2E in our plan.
- Beat them: PPTX fidelity (tables, charts, SmartArt fallback, slide transitions/animations metadata, embedded media extraction, autofit/line spacing) via a hybrid of structured text for editing plus rasterised slides through the PDFium/LibreOffice path we already bundle; FreeShow itself falls back to LibreOffice->PDF, which validates the hybrid.
- Match (table stakes they have): multi-destination RTMP with per-destination reconnect/backoff and hardware encoder auto-detect; display hotplug recovery with saved-screen-id fallback; NDI idle-aware frame rate (1 fps with no receiver); unchanged-frame skipping with keepalive; Bonjour discovery of remote servers; stage display with live output mirror; Companion-friendly action API; Planning Center sync; song/scripture/timer depth.
- Avoid copying their weaknesses: whole-state save with dropped concurrent saves, whole-cache IPC pushes, plaintext secrets store, god-store, dependence on personal-fork native addons.

### Gaps
- No head-to-head runtime benchmark was possible (static read-only analysis); performance statements come from code comments, not measurements.
- UI/UX quality, operator ergonomics and real-world reliability were not assessed (no issue-tracker mining).
