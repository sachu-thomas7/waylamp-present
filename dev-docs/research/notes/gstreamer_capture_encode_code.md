## 2. gst-plugins-rs net/webrtc: status and design of webrtcsink, whipclientsink, whipserversrc, webrtcsrc, signallers (WHIP/WHEP)

### Takeaway
`net/webrtc` (plugin `rswebrtc`) is a mature `webrtcbin` wrapper family: one `BaseWebRTCSink`/`BaseWebRTCSrc` pair with swappable `Signallable` GObject signallers, WHIP/WHEP implemented as signallers (client and server). The WHIP server is explicitly minimal: no auth/TLS, ICE trickle (PATCH) returns 501, and it is oriented around the element's own pad model rather than a multi-slot ingest registry like our `whip_server.rs`.

### Inferences
- Our F2.4 design (own axum 0.8 server with `POST /whip/{slot}`, 409 on a live slot, 503 beyond 4 slots, bearer token) is strictly ahead of `whipserversrc` on auth, slot accounting and trickle handling. gst's value is the client side (`whipclientsink` for loopback tests and as an egress WHIP client) and as a reference for the response contract (`201`, `Location`, `Link`, `406`).
- Our server returning `PATCH` as supported or 501 is a legitimate choice; the reference implementation also answers 501, so phones that require trickle ICE may rely on full-ICE offers. Not tested.
- The `webrtcsink` per-consumer pipeline model means a one-to-one WHIP egress is natural, but fan-out to several egress targets would duplicate encoders unless we encode once ourselves and feed pre-encoded caps.

## 3. webrtcsink: encoder selection/probing and congestion control / bitrate adaptation

### Takeaway
Encoder choice is rank-driven (GStreamer registry rank, MARGINAL and above) and then validated by actually running a short discovery pipeline sequentially per candidate; per-encoder property tables set low-latency CBR defaults; adaptation uses Google Congestion Control via `rtpgccbwe` (default) or a homegrown delay/loss controller, with resolution/framerate mitigation. There is no vendor detection and no explicit hardware-versus-software preference, and no Windows AMF/Media Foundation encoder in the property table.

### Cited Findings
- Candidate discovery: `static CODECS` builds `Codecs` for OPUS, MULTIOPUS, L24/L16/L8, VP8, H264, VP9, H265, AV1, RAW by calling `gst::ElementFactory::factories_with_type(ENCODER|DECODER|PAYLOADER|DEPAYLOADER, Rank::MARGINAL)`, which returns factories in descending rank. — [net/webrtc/src/utils.rs `CODECS`](file:///C:/Users/sachu/AppData/Local/Temp/claude/C--Users-sachu-Projects-streamdeck/48d0083c-0783-4c80-9099-4c6084c2794a/refrepos/gst-plugins-rs/net/webrtc/src/utils.rs)
- Encoder pick: `Codec::get_encoder_for_caps` returns the first (highest-rank) encoder factory whose src pad template intersects the codec caps and whose template caps are not ANY; `Codec::get_payloader_for_codec` does the same by `encoding-name`. A codec is encodable only if a payloader exists (`EncodingInfo`). — [net/webrtc/src/utils.rs `get_encoder_for_caps`, `Codec::new`](file:///C:/Users/sachu/AppData/Local/Temp/claude/C--Users-sachu-Projects-streamdeck/48d0083c-0783-4c80-9099-4c6084c2794a/refrepos/gst-plugins-rs/net/webrtc/src/utils.rs)
- Codec order policy: `select_codec` tries the codecs proposed by the remote offer in the order of the user's `video-caps`/`audio-caps` (comment: if the offer had VP8, VP9, H264 and `video-caps` had H264 then VP8, it tries H264, skips VP9, then VP8). ### Inferences
- Model to copy for F4.x auto-selection: (1) enumerate encoder factories by registry rank, (2) filter by codec caps and by an allow-list of known-good property mappings, (3) validate each candidate by constructing and running a tiny real pipeline, one at a time, treating bus errors as "reject", (4) cache the winner, (5) apply a per-encoder property table for low-latency CBR and per-encoder bitrate units. `webrtcsink` itself lacks (a) a user-visible override name and (b) any hardware-before-software policy beyond registry rank, which Sunshine and Cap both add (sections 6 and 7).
- On Windows, the GStreamer registry rank of `amfh264enc`/`mfh264enc`/`nvh264enc`/`qsvh264enc` is not visible in this repo, so webrtcsink's behaviour on Windows depends on installed plugin ranks. We should not rely on rank alone; we should set our own priority order and ranks (or construct elements by name).
- `rtpgccbwe` + `rtprtxsend stuffing-kbps` is only relevant for WebRTC; RTMP/SRT egress have no TWCC feedback, so bitrate adaptation for them has to come from queue depth/RTT/send-buffer signals that we implement ourselves (no equivalent in these repos).

### Gaps
- Actual registry ranks of encoders on Windows and whether `rtpgccbwe` ships in the official Windows installer were not verified.
- Whether `webrtcsink` correctly handles hardware encoders on D3D11 memory end to end was not tested.

- Could scap (MIT) be a dependency for macOS/Windows window capture? Technically yes, with these constraints:

- Cap's capability file is deliberately broad (`windows: ["*"]` plus `fs:write-all`); it should not be copied given our "capability minimalism" invariant.

- Cap's tests and real behaviour (window capture of DRM/protected windows, minimized windows) were not read or run; WGC cannot capture minimized windows (general platform knowledge, not shown in the repo).
- Whether Cap's Windows recorder always uses the Media Foundation MFT or the FFmpeg encoders by default (both exist) was not traced end to end.

## 8. DistroAV: NDI runtime loading, discovery and format handling (lessons for F2.2 without the SDK)

### Inferences
- For F2.2 we do not need the SDK present to ship: mirror the three-stage gate (locate, load, `initialize()` + minimum version) and surface each failure as a distinct `AppError` with a stable code and a link, then enable the source panel only on success. Our `UnavailableDiscovery` already matches the "degrade with a message" behaviour.
- Search locations to copy: env override (`NDI_RUNTIME_DIR_V6`), then OS defaults (`C:/Program Files/NDI/NDI 6 Runtime/v6` is the Windows runtime installer location in general NDI knowledge, but it is NOT shown in these repos; both plugins rely on the loader path/the env var set by the installer).
- Discovery should be a persistent find-instance with a periodic diff (gst plugin style) rather than DistroAV's create/destroy per refresh; the latter exists because it feeds a UI property list, not live state.
- Receiver controls worth exposing: bandwidth (`highest/lowest/audio_only`) for low-power preview versus program, latency preset, and a "lost source" policy with a 3-5 s timeout (DistroAV uses 3 s; gst `ndisrc` uses `timeout` 5000 ms and `connect-timeout` 10000 ms).
- Because the two reference implementations disagree on the hardware-acceleration metadata string, F2.2 should not depend on it; test with the SDK before adding it.

### Gaps
- NDI SDK license text unreadable (see section 1); redistribution of `Processing.NDI.Lib.x64.dll` inside our installer is therefore unverified, and both references avoid it by requiring a separate runtime install.
- DistroAV's output (sender) code, PTZ, and framesync internals were not read in detail.

### Inferences
Actionable adoption list (each item labelled by evidence):
1. F4.x encoder auto-select (high confidence from code): build `EncoderCandidate { name, element_factory, codec, platform, props_fn, flags }` entries in Rust; order by a fixed list, reordered by detected GPU vendor on Windows (Cap's four orderings); skip candidates whose factory is not present; validate each by running a short real pipeline (`videotestsrc ! convert ! enc ! parse ! appsink`), pull one buffer, assert it is a keyframe and parses, one candidate at a time (webrtcsink: "avoid NVENC collisions"; Sunshine: first packet must be IDR); cache; re-probe on GPU/display change; allow `[encoder] name = "..."` override in TOML with fallback to the list; publish `EncoderSelected/EncoderFailed` on the event bus with the failure reason.
2. Per-encoder low-latency property table (from `configure_encoder`) is directly reusable as data for NVENC (`rc-mode=cbr-ld-hq`, `zerolatency`), QSV (`low-latency`, CBR), VA (CBR), x264 (`zerolatency`, `ultrafast`). We still need AMF (`amfh264enc`) and Media Foundation (`mfh264enc`) rows, which no reference gives for GStreamer; Sunshine/Cap give FFmpeg-option analogues (`amdvce`: `latency`, `async_depth`, `skip_frame`; `mediafoundation`: `rate_control=cbr`, `scenario=display_remoting`).
3. F4.x bitrate adaptation: for WHIP egress, drive the encoder from `rtpgccbwe` estimates (only if GStreamer `rtp` plugin is shipped) with min/start/max bounds and a resolution/fps mitigation hook like `configure-mitigation-caps`; for RTMP/SRT, implement our own controller keyed on send queue growth (no reference code exists for it in these four repos).
4. F3.2: define a `CaptureTarget { Display, Window, Area }` enum like Cap's; Windows via WGC `CreateForWindow` (need a D3D11 device and adapter choice, skip software/virtual adapters, WARP fallback), macOS via SCK window filter plus `CGPreflightScreenCaptureAccess`; expose OS-version feature probes (border off, cursor toggle, min update interval) and a `closed` callback that raises a `SourceLost` event; handoff with a single-slot latest-frame buffer; exclude our own controller window from display captures on macOS.
5. F2.2: implement `libloading`-based lazy NDI load with the same search order and a version gate; keep discovery persistent with diff; expose bandwidth/latency/lost-source policy; treat HW-accel metadata as experimental.
6. F2.4: keep our axum server; borrow the `Link` header STUN/TURN response and 201/`Location` contract; keep `PATCH` as 501 or implement trickle, and note upstream also lacks it. Use `whipclientsink` only as a loopback test client (we already do per CLAUDE.md).
7. Licensing guardrails: do not copy Sunshine/DistroAV/Cap-AGPL code. If `scap-*` is vendored, keep `licenses/LICENSE-MIT` and copyright headers, avoid `cap-d3d-adapter`, and re-verify `scap-targets` license metadata first.
