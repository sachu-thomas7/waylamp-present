AI Context Handoff System

Expert framework for conveying project state to Claude or any AI coding assistant — efficiently, precisely, and without redundant regeneration across phase boundaries.

💡

The core problem: Every new AI thread starts cold. Without a structured handoff, you waste the first 20% of your context window re-explaining architecture, re-generating boilerplate, and correcting the model's wrong assumptions. This guide eliminates that waste.

🧠 The 5 Context Engineering Principles

Principle 01

State Over History

Never give the AI the full conversation history. Give it the current state: what exists, what works, what's broken, what's next. History wastes tokens; state gives direction.

Principle 02

Boundary Before Code

Always declare architecture invariants before asking for code. This prevents the model from generating patterns that violate your event-bus-only channel rule or process-separation constraint.

Principle 03

Scope Locking

Explicitly name what is OUT of scope for the current task. Claude will otherwise try to be helpful by touching adjacent systems — which breaks stable code you didn't want changed.

Principle 04

Acceptance Criteria First

Paste the exact acceptance criteria from the roadmap. The model generates toward measurable tests, not toward vague descriptions. This alone halves back-and-forth iterations.

Principle 05

Minimal Viable Context

Only include the subsystems the AI will touch in this session. Don't paste the full roadmap — paste only the current feature block plus its direct dependencies. Smaller context = sharper output.

Principle 06

Output Contract

Tell Claude exactly what files to produce and what to leave untouched. "Generate only X, modify only Y, do not touch Z" prevents the model from refactoring stable code mid-session.

📐 The 7-Block Context Anatomy

Every handoff prompt to Claude should follow this exact structure. Each block serves a distinct cognitive purpose for the model.

  1. 1

    🔖 Project Identity Block ~100 tokens

    Project name, tech stack summary (Tauri v2 / Rust / GStreamer / React), current phase, and one-sentence mission. Sets the model's entire reasoning frame.

  2. 2

    🏗️ Architecture Invariants Block ~200 tokens

    The 5 never-break rules (process separation, event-bus-only, config-as-code, coexistence-first, observability). Pasted verbatim every time. Guards against AI anti-patterns.

  3. 3

    ✅ Completed State Block ~150 tokens

    Bullet list of what's done and verified. Feature IDs (F0.1, F1.2…) + one-line status. No code — just confirmation of what the AI should treat as stable ground truth.

  4. 4

    🎯 Current Task Block ~300 tokens

    The single feature being built this session: description, technologies, and the exact acceptance criteria from the roadmap. This is the AI's primary directive.

  5. 5

    🔌 Interface Contract Block ~200 tokens

    Types, event variants, and Tauri command signatures that the current feature must integrate with. Only the interfaces — not the implementation. Prevents mismatched types.

  6. 6

    🚫 Scope Boundary Block ~50 tokens

    Explicit "DO NOT touch / generate / modify" list. Short but critical. Prevents Claude from helpfully refactoring things you didn't ask for.

  7. 7

    📦 Output Contract Block ~50 tokens

    Exact file paths to generate or modify. Expected response format (code only / code + explanation / tests only). This makes the output immediately usable.

⚠️ Context Anti-Patterns to Avoid

❌ Pasting the Full Roadmap

The 40KB roadmap eats your entire context window. The AI reads all of Phase 5 even when you're working on Phase 0. Paste only the current feature's section + the invariants header.

❌ "Continue from where we left off"

New threads have no memory. This prompt forces the AI to hallucinate the prior state. Always provide an explicit completed-features list instead — it takes 60 seconds and saves 10 minutes of corrections.

❌ No Scope Boundary Declaration

Without an explicit "do not touch" list, Claude will refactor your working IPC layer while implementing NDI discovery. It's being helpful — but it breaks stable code. Always lock scope explicitly.

❌ Vague Task Description ("implement NDI")

The AI will invent requirements. Paste the exact acceptance criteria from the roadmap — they're testable, specific, and already match your architecture. Verbatim beats paraphrased every time.

❌ Sharing Interface Details Inside Code Comments

If your interface contract is buried in code comments or inline, the model deprioritises it. Put types and event signatures in a dedicated block before any code. Named blocks = higher attention weight.

✅ Phase Completion Workflow

Run through this checklist at the end of every phase or sub-feature before starting the next AI session.

  • □
    All acceptance criteria tested — every bullet in the roadmap's AC section has a passing unit/integration test
  • □
    AppEvent enum reviewed — new variants are additive, #[non_exhaustive] is maintained, no variants removed
  • □
    TOML schema updated — any new config fields have default values and migration handled
  • □
    Feature flag verified — feature compiles independently under its Cargo feature flag (phase2, phase3…)
  • □
    External tools still operational — Mevo Studio / ProPresenter still work alongside the new feature
  • □
    CI passes — cargo test, cargo clippy -D warnings, npm run typecheck all green
  • □
    Observability wired — new subsystem errors surface as AppEvent within 100ms
  • □
    Update the completed-features list — add the new feature ID to your handoff template's Block 3

🛡️ Architecture Invariants (Copy-Paste Ready)

Always include Block 2 verbatim — these 5 rules prevent the most common AI-generated anti-patterns in a Tauri + GStreamer architecture.

## ARCHITECTURE INVARIANTS — include in every AI session 1. PROCESS SEPARATION: GStreamer pipeline runs in a dedicated Tokio task. Tauri UI events NEVER block the media pipeline thread pool. No GStreamer calls from command handlers — use PipelineService actor channel. 2. EVENT BUS ONLY: ALL state transitions (slide change, scene cut, stream start/stop) flow through tokio::sync::broadcast AppEvent enum. No direct function calls across subsystem boundaries. 3. CONFIG AS CODE: Pipeline topology, scene definitions, overlay zones, WHIP endpoints are TOML files. No hard-coded behaviour anywhere. WHIP bearer tokens go in OS keychain (keyring crate), never in TOML plaintext. 4. COEXISTENCE FIRST: New subsystems are additive. Mevo Studio and ProPresenter continue working until the phase that explicitly retires them. No breaking changes to external tool integration until the replacement passes all AC. 5. OBSERVABILITY FROM DAY ONE: All GStreamer bus messages (Error, Warning, Latency, QoS) translate to AppEvent variants visible in the controller UI. New subsystems must wire their errors to AppEvent within 100ms of occurrence.

⚡ Mini-Handoff Template (Sub-Feature / Bug Fix)

For single-file fixes or small sub-features, use this condensed version — same 7 blocks, just slimmer.

# STREAMDECK MINI HANDOFF — [sub-feature / bug] Stack: Tauri v2.11 · Rust 1.78 · GStreamer 1.26 · React 18 / TS 5 Invariants: Event bus only · GStreamer in own Tokio task · TOML config · no breaking external tool changes Stable: F0.1–F[LAST COMPLETED] all passing CI Fix/Task: [ONE SENTENCE — what exactly needs to change] File(s): src-tauri/src/[module].rs Must NOT change: [list of files/modules to leave untouched] AC: - [test condition 1] - [test condition 2] Output: Code diff / replacement block only, no prose
✅

Rule of thumb: If you can describe the task's acceptance criteria in under 5 bullet points, use the mini handoff. If the task touches 2+ subsystems or introduces a new module, use the full master template.
